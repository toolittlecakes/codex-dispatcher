# Ручная проверка follower-режима на реальной границе

Всё, что сделано в E8–E16, доказано тестами против настоящей библиотеки capnweb и грепом по бандлу расширения 26.803.61601. Живьём — телефон и окно VS Code как два клиента одной шины — не проверялось ни разу. Этот документ закрывает разрыв: каждый пункт даёт наблюдаемое условие успеха, которое видно в UI, без чтения кода.

Пока чек-лист не пройден, статус E8–E16 честно называть `prepared`, а не `готово`.

## Предусловия

- Codex VS Code extension **ровно 26.803.61601** (`~/.vscode/extensions/openai.chatgpt-26.803.61601-darwin-arm64`). Другая версия — другой контракт, проверка ничего не значит.
- Диспетчер и VS Code на **одной машине под одним пользователем**: шина — это unix-сокет `${CODEX_HOME:-~/.codex}/ipc/ipc.sock` (либо legacy `$TMPDIR/codex-ipc/ipc-<uid>.sock`, если на нём уже кто-то сидит), оба клиента резолвят его в одном порядке. Разные пользователи, машины или `CODEX_HOME` — разные шины, follower-режима не будет вообще.
- Телефон в той же сети (LAN-URL) либо доступ через relay.
- Не запускать две копии диспетчера: вторая займёт то же место на шине под другим clientId и картина станет нечитаемой.

## Подготовка

```bash
bun run doctor          # окружение
bun run start           # печатает Local: и Open from phone:
```

Открыть на телефоне напечатанный `Open from phone:` URL. Первая загрузка ставит cookie и вычищает токен из адреса.

Диагностика на протяжении всей проверки:

- вкладка с логом диспетчера в терминале (`[app-server]`, `[codex-ipc]`),
- `http://localhost:<port>/debug` в браузере ноутбука:
  - `bridge.ipc` — `socketPath` (на какой шине мы сидим), состояние подключения и кто ещё на ней: `peers` должен содержать окно VS Code сразу после его запуска, ещё до открытия треда,
  - `bridge.ownedThreads` — треды, которыми правит диспетчер, с ревизией и списком тех, кто на них подписан,
  - `bridge.mirroredThreads` / `bridge.threadOwners` — треды, которыми правит кто-то другой,
  - `hostErrors` — **должен оставаться пустым**; всё, что там появляется, — баг моста, даже если UI выглядит нормально.

## Проверка 0. Канал вообще жив (E8)

Это ворота: если провалилось, остальные пункты бессмысленны, потому что в вебвью всё, что связано с IPC, обёрнуто в `?.` и молча ничего не делает.

1. На телефоне открыть любой тред и отправить сообщение.
2. В VS Code открыть **тот же** тред.

**Успех:** окно VS Code показывает живой поток турна — токены идут по мере генерации, а поле ввода в режиме follower'а. **Провал:** VS Code показывает статичный тред или начинает свой турн.

## Проверка 1. VS Code не уводит тред у телефона (E10)

1. На телефоне запустить **длинный** турн (что-то на минуту работы).
2. Пока турн идёт, в VS Code открыть этот тред из списка.

**Успех:** VS Code подключается как follower, телефон продолжает стримить без разрыва, турн доходит до конца на телефоне. **Провал:** телефон теряет поток на середине, VS Code перехватывает тред себе.

## Проверка 2. Стоп из VS Code по треду телефона (E11)

Во время турна из проверки 1 нажать «стоп» в окне VS Code.

**Успех:** турн останавливается, оба клиента показывают его прерванным, ошибок в UI нет. **Провал:** ошибка вида «The buffered turn is no longer active» или молчание с продолжающимся турном.

## Проверка 3. Смена модели/режима с обеих сторон (E12)

1. В VS Code (follower) переключить collaboration mode (например, на plan) и модель.
2. Проверить телефон.
3. Запустить следующий турн **с телефона**.

**Успех:** телефон показывает новый режим и модель сразу после переключения; следующий турн идёт на выбранной модели (видно в шапке треда и в ответе). **Провал:** телефон остался на старом режиме, либо режим на секунду сменился и откатился, либо турн ушёл на старой модели.

Симметрично: переключить режим на телефоне и убедиться, что VS Code это увидел.

## Проверка 4. Загрузка полной истории длинного треда (E14)

Нужен тред, у которого чтение полной истории заведомо дольше 10 секунд (много длинных турнов; подойдёт долгоживущий рабочий тред).

1. Открыть его на телефоне как follower треда, которым владеет VS Code (или наоборот).
2. Проскроллить вверх до подгрузки полной истории.

**Успех:** история догружается целиком, сколько бы это ни заняло. **Провал:** через ~10 секунд ошибка/пустота, а в худшем случае follower решает, что владелец пропал, и забирает тред себе.

## Проверка 5. Стоп в момент завершения турна (E15, E16)

Гонка, её нужно ловить: отправить короткий запрос («скажи привет») и нажать «стоп» ровно в момент, когда ответ дописывается. Повторить 5–10 раз, с телефона и из VS Code.

**Успех:** ни одна попытка не даёт ошибки в UI — либо турн останавливается, либо он уже закончился и это просто ничего не меняет. **Провал:** всплывает `turn/interrupt: no active turn to interrupt` или «no active turn to steer».

## Что этим сценарием не проверяется

- **E13** (ревизия по треду, владение которым уехало во время чтения) — гонка, руками не воспроизводится осмысленно. Остаётся на уровне чтения кода и гарда.
- **Остальные сервисы RPC-сессии** (`openIn`, `github`, `fileAttachments`, `workspaceFiles`, `clipboard`, `appInfo`) хост не реализует. Соответствующие кнопки в UI дадут ошибку — это ожидаемо и не является провалом проверки (см. E8).

## Если что-то не сошлось

1. `hostErrors` в `/debug` — первое место, где виден отказ моста.
2. `[codex-ipc]` в логе диспетчера — проблемы самой шины.
3. Версия расширения: `ls ~/.vscode/extensions | grep chatgpt`. Не 26.803.61601 — проверка недействительна.
4. Разделить «канал мёртв» и «канал жив, но не то делает» помогает `bridge` в `/debug`: пустой `peers` — окно VS Code вообще не на шине (сверить `socketPath` с тем, что резолвит расширение: разные `CODEX_HOME` — разные сокеты); тред в `ownedThreads` с пустым `followers` — VS Code не объявил following, значит канал координации не доехал; тред в `mirroredThreads` — владение уехало, смотреть, почему.

## Результаты прогона 2026-08-13

Стенд отличается от описанного выше, и это надо держать в голове при чтении результатов. Изолированный `CODEX_HOME=/tmp/claude/codex-test-home` (`auth.json` и `config.toml` — симлинки на настоящие, так что шина отдельная, а аккаунт тот же), owner — диспетчер на 8792, follower — **второй диспетчер** на 8793 на той же шине, оба вебвью открыты в отдельном Chrome. Следствия:

- Потребитель снапшота — настоящий бандл расширения 26.803.61601, тот же самый; отличается **хост** под ним (наш `webview-rpc` вместо `wq` из `out/extension.js`). Для контракта снапшота это неважно (падало вебвью, не хост), для проверки хостовых веток — важно.
- Два диспетчера на одном хосте делят cookie (она на имя хоста, не на порт), поэтому вкладки разведены на `127.0.0.1` и `localhost`. Иначе вторая вкладка выбивает первую в 401.
- Разводить их по LAN-адресам (`192.168.x.x`, `10.8.x.x`) нельзя: там вебвью не поднимается вообще — не secure context, нет `crypto.randomUUID`. Это E25, и это же ломает штатный сценарий «открыть с телефона». Третий и четвёртый хосты пришлось брать из `*.localhost`.
- Окно VS Code в отдельном профиле в этот прогон так и не подняло Codex-UI: вебвью висит на сплэше «Codex in your IDE», чат не монтируется, `[IpcClient] Received broadcast but no handler is configured` — то есть расширение на шине, но вебвью до него не доехало. Своё основное окно пользователя не трогали намеренно.

## Прогон 2026-08-14: проверка 5 и поправка к проверке 4

Стенд тот же (owner и follower — два диспетчера на одной шине, оба вебвью в отдельном Chrome, вкладки не поднимаются на передний план), но роли за ночь поменялись: тредом владел 8793, а 8792 был follower'ом. Турны отправлялись с follower'а.

**Поправка к проверке 4, важнее её самой.** «Тред на 109 турнов не отрисовывается» — артефакт измерения, а не баг. Драйвер читал `document.body.innerText`, а `innerText` требует layout, которого Chrome не считает для вкладки, ни разу не выведенной на передний план: у нормально отрисованного треда `innerText` = 81 символ при `textContent` = 1864. То есть «пустое тело» означало «вкладка фоновая», а не «вебвью ничего не нарисовал». Всё, что в прошлых прогонах читалось через `innerText`, надо перечитывать через `textContent`; выводы, где содержимое сравнивалось с ожидаемым и совпадало, остаются в силе, а вывод «пусто» — нет. Про сам длинный тред вывод теперь: не проверен.

**Проверка 5 — частично.** Прицельный клик по стопу автоматизировался хуже всего, и по понятной причине: синтетические события в фоновой вкладке доходят до DOM, но состояние редактора композера синхронизируется только со вставкой, заменяющей выделение (первая вставка в пустой композер не регистрируется приложением вообще), а короткий ответ («hi») укладывается в ~2.5 с целиком, так что окно для попадания в момент завершения — десятки миллисекунд. Что получено за прогон:

- Стоп, нажатый в середине турна, работает с обеих сторон: клик на 1.3 с при естественном завершении на 2.3 с и на 3.4 с при завершении на 4.4 с — турн обрывается, ошибок в UI ни у owner'а, ни у follower'а нет.
- Клик на 2.6 с при среднем завершении ~2.9 с — обрыв без ошибок.
- Несколько раундов клик пришёлся уже после завершения турна (кнопки нет) — это не отказ, но и не проверка гонки.
- `hostErrors` пуст с обеих сторон на протяжении всего прогона; ни `no active turn`, ни `buffered turn`, ни error boundary ни разу не всплыли.

Чего не получено: попадания в тот самый момент, когда последний токен уже записан, а турн ещё не закрыт. Триггер «жать стоп на появление последнего токена» упёрся в то, что маркер приходится искать в тексте страницы, а страница содержит и сам промпт; версия со счётом вхождений уронила драйвер по protocol timeout.

**Проверка 5 — закрыта, но не кликом.** Трассировка окна жизни кнопки по событиям owner'а (`window.ts`) показала, почему клик в щель не проходит: `item/started(agentMessage)` → `item/agentMessage/delta` → `item/completed(agentMessage)` → `turn/completed` приходят одним батчем в пределах 1 мс, и кнопка «Stop» пропадает вместе с последней дельтой. То есть щели, в которую просят кликнуть, в UI не существует — не «трудно попасть», а не во что попадать. Последний момент, когда кнопка ещё есть, — фаза размышления до появления ответа.

Поэтому гонка проверялась тем запросом, который кнопка и отправляет: follower'ский `thread-follower-interrupt-turn-for-host` (`{conversationId, mode: "user-stop", expectedTurnId}`), отправленный из вебвью follower'а по событию owner'а. 14 раундов:

- в середине турна — `200 {"interruptedTurnId": "<turn>", "ok": true}`, турн обрывается;
- ровно по `turn/completed` (4 раунда) и через 400 мс после (2 раунда) — `200 {"interruptedTurnId": null, "ok": true}`: наша копия треда к этому моменту уже без активного турна, до app server запрос не доходит, ошибки нет, UI ничего не рисует;
- по последней дельте (6 раундов) — 2 раза `200` с реальным `interruptedTurnId` (запрос успел в живой турн), **4 раза `433 No IPC owner for thread …`**.

`hostErrors` пуст с обеих сторон во всех раундах, `Oops`/`no longer active`/`buffered turn` не всплывали ни разу. То есть E15/E16 в части «стоп по завершившемуся турну» ведут себя как задумано, а вот `No IPC owner` — отдельный дефект, найденный этой проверкой (см. ниже).

### Побочная находка: follower теряет владельца треда посреди турна

В логе follower-диспетчера (8792) во время турна идут подряд:

```
Failed to apply IPC patches for 019ffc74-…: Patch path does not exist
Received IPC patches before snapshot for 019ffc74-…
```

`applyIpcBroadcastEffects` на неудачном патче делает `streamOwners.delete(threadId)` (`src/server.ts:273`), то есть **забывает, кто владеет тредом**, и зеркало не восстанавливается: все следующие патчи падают уже в «before snapshot». После этого любой follower'ский запрос к владельцу — стоп, steer, компакт — получает `433 No IPC owner for thread …`, что и дало 4 из 6 отказов выше.

Патчи при этом шлём не мы: диспетчер-владелец рассылает только снапшоты (`buildDispatcherSnapshotParams`), а `thread-stream-state-changed` с `type: "patches"` уходит на шину от самого вебвью через `broadcastForWebview`.

**Как это устроено в VS Code.** Патчи в экстеншене шлёт именно вебвью — `canBroadcastIpcStatePatches` = «моя роль по этому треду owner и у меня есть followers», — а extension host только перекладывает их на шину (`threadStreamStateChanged`). То есть трафик вебвью законен, и запрещать его было бы неправильно. Разбирает патч follower так:

```js
if (r?.role !== "follower" || r.ownerClientId !== n || this.streamRevisionByConversationId.get(e) !== t.baseRevision) return;
try { setConversation(Hne(i, t.patches)) } catch (e) { $.warning("Failed to apply patches for", …) }
```

Три проверки перед применением — я follower, отправитель тот, кого назвал последний снапшот, и `baseRevision` совпадает с моей ревизией — и всё, что их не прошло, **молча игнорируется**. Владельца называет только снапшот, и ни одна ветка владельца не снимает; упавший патч — только warning, состояние остаётся прежним до следующего снапшота.

**Исправлено по этому контракту** (`src/thread-mirrors.ts`, вызов в `src/server.ts`): зеркала, их ревизии и владельцы живут за одним объектом `ThreadMirrors`, который применяет патчи только от записанного владельца и только с совпадающей базой, а неудачный патч оставляет зеркало устаревшим и возвращает `patch-failed`. Состояние вынесено из `server.ts` именно затем, чтобы «забыть владельца из-за патча» стало структурно невозможным, а не просто не написанным: снаружи класса нет способа удалить владельца иначе, чем по дисконнекту клиента. Повтор тех же 6 раундов по последней дельте на исправленной сборке: **6 из 6 → `200` с реальным `interruptedTurnId`** (было 2 из 6), в логе follower-диспетчера ноль `Failed to apply IPC patches`, ноль `Received IPC patches before snapshot`, ноль `No IPC owner`; `hostErrors` пуст с обеих сторон.

## Прогон 2026-08-14, вечер: рестарт диспетчера под живой страницей

Сценарий «жму, ничего не происходит»: диспетчер перезапущен, вкладка осталась открытой — её capnweb-сессии жили в убитом процессе, EventSource переподключался к новому, и каждый запрос вебвью тихо повисал (у владельца копились `No webview RPC session`). VS Code при рестарте extension host принудительно перезагружает вебвью; наш эквивалент — `hostInstanceId` на процесс: он вшивается в HTML и приходит первым кадром каждого SSE-подключения (без `id:`, чтобы не двигать Last-Event-ID), и страница, увидев чужой id, перезагружает себя.

Проверено на живом стенде: маркер в `window` до рестарта — после рестарта маркер пропал (страница перезагрузилась сама), композер жив, отправка «say the word kiwi» ушла и ответ пришёл без единого касания вкладки; `__codexHostAdapterClientErrors` пуст.

**Граница (ревью thr_szqxkcki5h):** на direct/LAN-пути токен раньше генерился заново на каждый запуск CLI и не сохранялся, поэтому после рестарта кука страницы была мертва: реконнект SSE получал 401, который EventSource не ретраит, и instance-событие не приходило. Закрыто в `ensureWebviewToken` (`src/dispatcher-config.ts`): токен минтится один раз и живёт в `~/.codex-dispatcher/config.json` (0600) рядом с relay-логином, так что рестарт больше не меняет его и reload по чужому `hostInstanceId` работает и на LAN. Оверлей «The connection to Codex was lost…» остаётся для действительно терминальных случаев (например, токен вручную сброшен). На relay-пути reload работал и раньше: браузерная сессия живёт в relay, и он подставляет свежий токен сам.
