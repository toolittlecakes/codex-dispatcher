Прошло независимое ревью субагентом (одна итерация, 2026-08-12): все findings подтверждены фактически, поправки внесены inline (A6 понижен, C3-коллизия кук повышена), добавлена секция E с пропущенными изначально проблемами.

## A. Fidelity бриджа к VS Code host (высокий приоритет)

### A1. Два несинхронизированных канала доставки сообщений в webview — DONE

В VS Code webview↔host — один упорядоченный FIFO-канал `postMessage`. В бридже два: ответы на host-message приходят в POST response (`deliver(body.messages)` в shim, `extension-webview.ts:986-1005`), broadcast'ы — через SSE (`:1023`). Плюс каждый `postMessage` из webview — отдельный параллельный fetch: порядок обработки на сервере и порядок доставки ответов не гарантирован. Симптом: редкие гонки состояния/стрима, которых нет в VS Code (notification о turn приходит раньше ответа на запрос, который его запустил, и т.п.).

Направление фикса: один упорядоченный канал (например, весь трафик через один WebSocket с seq-номерами) либо очередь на клиенте (сериализовать `sendHostMessage`) + доставка ответов через тот же SSE-поток, чтобы сервер контролировал порядок.

Сделано (host→webview): POST `/host-message` больше не возвращает сообщения — только `{ accepted: true }`. Все исходящие сообщения (и ответы, и broadcast'ы) идут одним потоком с общей seq-нумерацией, поэтому порядок доставки задаёт сервер, а не гонка параллельных fetch'ей. Шим генерирует `clientId` (`crypto.randomUUID`), передаёт его в `x-dispatcher-client` на POST и в `?client=` на `/events` — так ответ попадает именно в поток той вкладки, которая спросила, а не «куда-нибудь». Буфер/`Last-Event-ID` из A2 стали per-client: `StreamClient { seq, buffer, controller, detachedAt }`; отсоединённые клиенты держатся 5 минут (чтобы пережить блокировку экрана) и потом собираются `pruneDetachedClients`. Побочный эффект, соответствующий реальному хосту: инициатор `persisted-atom-update` теперь тоже получает `persisted-atom-updated` — в VS Code экстеншн так же постит в webview, из которого пришло обновление.

**Правки после ревью (три регрессии/дыры первой версии):** (1) гонка «POST раньше первого `/events`» — EventSource подключается асинхронно, вебвью успевает спросить до открытия потока, ответ буферизовался, а свежее подключение без `Last-Event-ID` буфер игнорировало и слало resync — ответ терялся навсегда. Теперь подключение без `Last-Event-ID` при нетронутом буфере (первый элемент всё ещё `id: 1`) проигрывает буфер целиком: «не видел ни одного события» + «ничего не вытеснено» = буфер и есть ровно пропущенное. (2) `cancel` мёртвого сокета срабатывает уже после реконнекта и убивал *новый* живой поток (обнулял controller и heartbeat) — вкладка немела до перезагрузки; теперь `detachIfCurrent` рвёт клиента только по тому controller'у, который сейчас привязан. (3) вкладка, которая сделала POST и больше никогда не открывала `/events`, не собиралась никогда: `pruneDetachedClients` звался только при открытии потока. Добавлен prune в `broadcast` — единственное место, куда мы ещё попадаем после закрытия вкладки. Не принято из ревью: «resync-фреймы делят один event id» — это намеренно, id на снапшоте означает текущую позицию потока, чтобы реконнект после resync не запросил повтор уже пересланного.

Сделано (webview→host): вторая половина канала. Раньше каждый `postMessage` был отдельным параллельным `fetch` — порядок прибытия задавала сеть. Теперь у шима один outbox и ровно один запрос в полёте: пока он летит, сообщения копятся и уходят следующим батчем (`{ messages: [...] }`), так что порядок отправки == порядок прибытия, а всплеск на бутстрапе не превращается в цепочку последовательных round-trip'ов. На хосте POST больше не ждёт обработку: сообщения батча *стартуют* по порядку (`dispatchHostMessage` без await) и отвечают когда ответят — это и есть семантика VS Code, где handler вызывается строго по порядку, но канал не блокируется на его async-работе. Если бы POST ждал обработку, один внешний fetch (до 25s) вешал бы весь канал. Следствие: `{ accepted: true }` означает «принято к обработке», ошибки приходят в поток как `host-message-error`.

**Вторая итерация ревью — ещё три дыры.** (1) Реплей буфера на свежем подключении *заменял* resync-снапшот вместо того, чтобы дополнять его: в том же окне гонки вкладка получала свои ответы, но теряла pending approvals (без них turn стоит без промпта). Теперь буфер и resync идут вместе, буфер первым (он старее), resync последним как актуальное состояние; ранний `return` остался только для настоящего resume. (2) Нумерация событий живёт внутри одной инкарнации клиента, а браузер помнит `Last-Event-ID` через prune клиента (вкладка в фоне >5 мин) и через рестарт диспетчера: старый id либо уводил в resync с потерей уже забуференных ответов, либо (если старый id < нового seq) молча выкидывал начало новой нумерации. Теперь у клиента есть `epoch`, event id — `epoch.seq`, и resume принимается только при совпадении epoch, иначе это свежий поток. (3) Шим не смотрел на HTTP-статус ответа `/host-message` — батч из N сообщений мог исчезнуть без следа (400 от старой вкладки после апгрейда, 401 по протухшей cookie); теперь не-2xx поднимает ошибку по каждому сообщению батча. Плюс сериализация теперь по одному сообщению, чтобы несериализуемое значение роняло только себя, как `postMessage` в VS Code, а не соседей по батчу. Ответ на битый батч больше не притворяется `fetch-response` с `requestId: undefined` — это `host-message-error`.

**Третья итерация ревью.** (1) `pruneDetachedClients` звался *после* `clientFor` — вкладка, проспавшая больше 5 минут, переподключалась к записи, которую тут же удаляли из мапы: стрим жив, heartbeat идёт (браузер не видит обрыва), но broadcast'ы её не находят, а следующий POST заводит новую запись — молчаливый вечный столл. Prune теперь идёт первым, стухшая запись честно умирает и вкладка получает свежий поток с resync. (2) Все сообщения resync уходили с одним id (seq не рос), поэтому обрыв в середине снапшота был неотличим от «получил весь снапшот»: реконнект по этому id возвращал пустой diff и хвост (в т.ч. pending approvals) терялся навсегда. Теперь resync идёт через обычный `send` — со своими номерами и в буфере, так что обрыв посреди снапшота нормально доигрывается. (3) `JSON.stringify` возвращает `undefined` (а не бросает) для `undefined`/функции/символа — такое сообщение делало тело батча невалидным JSON и топило соседей; теперь шим бросает сразу у вызывающего, как `postMessage` в VS Code роняет только своего caller'а.

Известная дыра покрытия: сам шим — инлайновая строка, юнит-тестами недостижим (проверка `response.ok`, outbox, сборка тела). Тестируется только серверная половина канала.

Попутно починен тестовый хелпер `openEventStream`: брошенный по таймауту `reader.read()` всё равно съедал следующий чанк, и события молча терялись — теперь один read держится в полёте между итерациями опроса.

### A2. Потеря событий при SSE reconnect — DONE

EventSource авто-реконнектится, но нет Last-Event-ID/буфера: всё, что broadcast'нулось во время разрыва (блокировка телефона убивает соединение), теряется. Replay при реконнекте (`buildExtensionEventReplayMessages`, `server.ts:781`) отдаёт только thread-stream снапшоты; `mcp-notification` и `mcp-request` (pending approvals!) от app-server не реплеятся — тихая потеря. Дополнительно: шим не вешает `events.onerror` — перманентная смерть SSE-соединения тоже тихая для пользователя.

Сделано: каждое исходящее SSE-сообщение получает монотонный `id`, последние 500 держатся в ring-buffer'е, а реконнект с `Last-Event-ID` догоняет ровно пропущенное. Если разрыв не покрывается буфером (или id вне диапазона) — явный полный resync из текущего состояния. В replay добавлены pending server requests (аппрувы/элиситации), иначе после реконнекта turn стоял бы без промпта. Шим получил `events.onerror`, чтобы смерть стрима перестала быть неотличимой от тишины.

### A3. `handleMcpResponse` выбрасывает error из ответа webview — DONE

`extension-webview.ts:670`: `respondToServerRequest(String(response.id), response.result ?? null)` — если webview ответил на server request с `error`, app-server получает успешный `result: null`. Молчаливое искажение. `CodexAppServer.respondToServerRequest` вообще не умеет передавать error.

Фикс: пробрасывать `error` в JSON-RPC ответ app-server'у.

### A4. `handleExternalFetch` не эквивалентен настоящему fetch — DONE

- При `!response.ok` тело ответа выбрасывается, возвращается error со `statusText` (`extension-webview.ts:1262`). Реальный fetch отдаёт body и на 4xx/5xx; экстеншн может парсить JSON ошибки.
- Жёсткий `AbortSignal.timeout(10_000)` на все внешние запросы — долгие запросы отваливаются.
- Полная буферизация ответа — стриминговые ответы не работают.

Контракт подтверждён по бандлу экстеншна (`onFetchResponse`, `openai.chatgpt-26.803.61601`): при `responseType: "success"` вебвью резолвит 2xx через `JSON.parse(bodyJsonString)`, а любой другой статус реджектит как `new Pd(bodyJsonString, status)` — т.е. тело non-2xx ответа и есть текст ошибки. `responseType: "error"` (с опциональным `errorCode`) предназначен для несостоявшегося обмена.

Сделано: любой завершившийся HTTP-обмен возвращается как `success` с реальным статусом и телом (`readExternalFetchBody`); `error` остался только для транспортных сбоев. По стримингу решение зафиксировано: host-стриминг не нужен — `fetch-stream-*` сообщения генерирует websocket-путь внутри самого вебвью, а контракт `fetch` — строго request/response.

**Осознанное отклонение от реального host (уточнено ревью):** настоящий VS Code host в `out/extension.js` тоже отдаёт non-2xx как `responseType: "error"` со `statusText` и тело выбрасывает. Наш вариант остаётся внутри того же контракта вебвью, но даёт строго более информативный reject (тело вместо `statusText`) — отклонение намеренное и зафиксировано здесь, а не случайное.

**Таймаут — правка после ревью.** Первая версия подняла таймаут 10s → 120s и этим сломала relay-путь: `fetch-response` едет в теле POST `/host-message`, relay сдаётся через 30s (`startTimeout`) и шлёт `http-request-cancel`, а вебвью settle'ит pending fetch только по приходу `fetch-response` — в окне 30–120s промис висел бы вечно. Раньше инвариант `host < relay` держался случайно (10s < 30s). Итог: таймаут 25s, ниже самого строгого звена цепочки (relay `startTimeout` 30s, Bun `idleTimeout` 60s), инвариант зафиксирован комментарием в коде. Развязать это ограничение может только A1 (унести `fetch-response` из тела POST в общий поток).

**Follow-up (pre-existing, не блокер):** реальный host на 401 делает token-refresh и backoff-ретраи retryable-статусов — эмуляция этого не делает, так что 401 долетает до вебвью как reject вместо тихого рефреша.

### A5. Version coupling с экстеншном без контракта — DONE

Бридж жёстко завязан на контракт конкретной версии экстеншна: списки `vscode://codex/*` endpoints (`handleVSCodeRequest`), follower-методы, `methodVersions` (`thread-stream-state-changed: 6`, захардкожен также в `server.ts:801`), wham/statsig стабы. При этом `resolveExtensionWebviewRoot` берёт последнюю установленную версию экстеншна — автообновление ломает бридж молча (`Unsupported vscode://codex/...`). Уже копятся version-specific хаки: strip `workspace_dependencies` (`extension-webview.ts:1397`), кэш `experimentalFeature/enablement/set` (`:627`). Мелочь рядом: `extensionVersion()` (`extension-webview.ts:1611`) пересканирует диск и может разойтись с `webviewRoot`, зарезолвленным при старте.

Фикс: пиннинг поддерживаемой версии экстеншна (диапазон) с явной ошибкой при несовпадении + smoke/contract-тест против реально установленной версии.

Сделано: диапазон поддерживаемых версий зафиксирован в коде (`supportedExtensionVersions`, сейчас 26.422.x — 26.803.x: нижняя граница — версия, против которой делался UI-parity, верхняя — последняя проверенная end-to-end). Автодискавери больше не берёт «просто самую свежую установленную», а выбирает самую свежую *поддерживаемую*; если установлены только версии вне диапазона — явная ошибка с перечислением найденного вместо молчаливого `Unsupported vscode://codex/...` где-то в середине сессии. `doctor` показывает это как FAIL с текстом ошибки, а не падает. Явный `CODEX_EXTENSION_WEBVIEW_ROOT` остаётся способом сказать «знаю, что делаю» — версионная проверка к нему не применяется. Сканирование вынесено в чистую `selectExtensionWebviewRoot(extensionsDir)`, поэтому выбор версии тестируется на настоящей файловой системе, а не на моках; отдельный smoke-тест падает, если экстеншн, реально установленный на машине, вышел за диапазон. Правки после ревью: `serve --install-extension` на чистой машине ставил marketplace latest, который пиннинг тут же отверг бы — теперь ставится ровно проверенная версия (`openai.chatgpt@26.803.61601`), и `doctor` пишет её же. И убран тихий fall-through: `CODEX_EXTENSION_WEBVIEW_ROOT` с опечаткой раньше молча игнорировался и уходил в автоскан (оператор ставил override именно чтобы запустить unsupported-версию — и получал ошибку про неподдерживаемую версию), теперь это явная ошибка про отсутствующий `index.html`. Заодно `extension-info` больше не пересканирует диск: версия выводится из уже зарезолвленного `webviewRoot` (`extensionVersionOf`), так что разойтись они больше не могут.

### A6. Debounce вместо throttle в `scheduleDispatcherOwnedRefresh` — DONE

`server.ts:723`: каждый notification ресетит 120ms таймер. При стриме чаще 120ms refresh откладывается до паузы — starvation: VS Code-follower dispatcher-owned треда видит фриз, потом скачок. Поправка по итогам ревью: `dispatcherOwnedConversations` наполняется только из мёртвого WS-протокола (см. B1/E3), так что симптом сейчас недостижим — чинить вместе с решением по E3.

Фикс: trailing throttle (гарантированный refresh не реже, чем раз в N ms), не debounce.

Сделано вместе с E3 (подсистема ожила, значит starvation стал достижим): первый notification ставит таймер, последующие в окне его не сдвигают, `delayMs = 0` (аппрувы) по-прежнему вытесняет отложенный refresh. На живом прогоне один turn дал 7 снапшотов вместо одного в конце.

## B. Мёртвый код

### B1. `canHandle` всегда true → `public/` и WS-протокол недостижимы — DONE

`extension-webview.ts:168`: `canHandle` = `pathname.startsWith("/")` — всегда true. Следствия:

- `serveStatic` и весь `public/` (legacy UI: `app.js`, `index.html`, `styles.css`, `sw.js`, `manifest.webmanifest`, `approval-requests.js`) не отдаются никогда. Исключение — `json-patch.js`, который сервер импортирует напрямую.
- PWA manifest и service worker не отдаются: если PWA-установка заявлена как фича — она сломана.
- Почти весь WS-протокол `ClientMessage` в `server.ts` (~400 строк: listThreads/startTurn/rotateToken/...) обслуживает мёртвый UI.

Решение нужно явное: либо выпилить legacy UI + мёртвую часть WS-протокола (и перенести `json-patch.js` в `src/`), либо это баг routing'а и PWA-ассеты надо начать отдавать. Blast radius больше, чем кажется: вместе с WS-протоколом мертва вся dispatcher-owner подсистема — см. E3.

Сделано (решение пользователя: выпилить UI, PWA сделать по-настоящему). Удалены `public/`, `serveStatic`, `/ws` и весь `ClientMessage`-протокол вместе с осиротевшими хелперами (`securitySnapshot`, `broadcastSecurity`, `markDispatcherOwner*`, `ensureDispatcherOwnedConversation`, `scheduleRefreshForServerRequest`); `json-patch` переехал в `src/json-patch.ts` с типами (закрывает D2). `DISPATCHER_REMOTE_URL` больше некому читать — убран и из `cli.ts`. stderr app-server'а и IPC писались только в мёртвый UI — теперь идут в консоль.

PWA сделан на поверхности вебвью (`src/pwa.ts`): `/manifest.webmanifest`, `/sw.js` и `/icon.png` (иконка берётся из самого расширения, 385x385) отдаются без токена — браузер тянет манифест без нашей куки; в `<head>` инжектятся link'и, apple-touch-icon и регистрация worker'а. Worker намеренно ничего не кэширует (кэш отдавал бы ассеты версии расширения, которую диспетчер больше не хостит) — только `fetch`-listener ради installability. Кука сессии получила `Max-Age`, иначе установленное приложение стартовало бы с `start_url` в 401. Проверено живьём: манифест/worker/иконка отдаются анонимно, `/` без токена — 401, `/ws` — 404.

### E6. `dispatcherOwnedConversations` растёт монотонно (найдено ревью E3)

Записи владения не удаляются ни по какому таймауту: удаление есть только при передаче владения окну VS Code (`releaseDispatcherOwnership`). Каждая запись после refresh держит полные turns; `client-status-changed: connected` рассылает снапшоты по всем накопленным тредам, а `buildExtensionEventReplayMessages` реплеит их все каждому подключающемуся webview. В долгоживущем процессе память и объём реплея растут с каждым тредом, который телефон когда-либо вёл.

Решение нужно явное, потому что любое вытеснение — это молчаливая потеря владения для follower'а, который в этот момент смотрит тред. Варианты: (а) отпускать владение по неактивности треда (нужен порог), (б) ограничить число owned-тредов LRU-кэпом, (в) реплеить webview только треды, которые он реально открывал. Не выбрано.

### E7. Пересекающиеся refresh'ы owned-треда (найдено ревью E3)

`scheduleDispatcherOwnedRefresh` удаляет таймер из map до `await thread/read`, поэтому второй refresh может стартовать, пока первый в полёте; при завершении не в порядке отправки старый снапшот перезапишет более новый. Самолечится следующим событием треда. Не проверено, гарантирует ли app-server порядок ответов.

## C. Security

### C1. Relay: response-фреймы не привязаны к сессии отправителя — DONE

`relay-server.ts:94-96`: `message(_ws, raw)` игнорирует, от какого сокета пришёл фрейм. Любой авторизованный dispatcher может слать `http-response-*` с чужим requestId (cross-tenant response injection). Сдерживается только энтропией `req_<24 bytes>`.

Фикс: в `handleDispatcherFrame` проверять `pending.dispatcherSessionId === ws.data.session.id` (сделано через `pendingRequestForDispatcher`). Заодно закрыт сопутствующий риск: `decodeRelayFrame` кидал на битом фрейме прямо в ws-обработчике — теперь такой фрейм закрывает сокет нарушителя, а не всплывает наружу.

### C2. `pendingOAuthByState` без TTL-очистки

`relay-server.ts:39`: `createdAt` пишется, но не проверяется; записи брошенных логинов копятся вечно. Фикс: TTL-чистка (например, при каждом start/callback выкидывать записи старше 15 минут).

### C3. Мелочи

- Сравнение dispatcher-токена не constant-time (`extension-webview.ts:240-247`, а также `/ws` в `server.ts:199`) — заменить на `crypto.timingSafeEqual`.
- Кука дispatcher'а без `Secure`/`Max-Age` (`authCookie`, `extension-webview.ts:1658`). Нюанс: локальный сценарий — http по LAN, `Secure` там сломает вход; ставить флаг только когда запрос пришёл через relay/https.
- **Коллизия имён кук — повышена по итогам ревью, достижима.** Имя `codex_dispatcher_session` совпадает у relay (Domain-кука на `.codex-dispatcher.app`, `relay-server.ts:496`) и дispatcher'а (`extension-webview.ts:54`). Если пользователь откроет через relay URL с `?token=` (dispatcher отдаст свой `set-cookie` в `serveIndex`, `extension-webview.ts:263-265`), браузер получит две одноимённые куки, и `cookieValue` relay (`relay-server.ts:507`) возьмёт первую попавшуюся → ломается relay-авторизация. Переименовать одну из кук.

Второй инстанс `ExtensionWebview` (тесты) клобает первый; конструктор молча перезагружает глобальное состояние. Фикс: перенести в поля класса / отдельный state-объект, инжектируемый в конструктор.

## E. Добавлено по итогам ревью субагентом (пропущено в первом проходе)

### E1. Relay: `http-response-error` после `http-response-start` вешает браузерный стрим — DONE

`relay-server.ts:373-381`: при error-фрейме вызывается `pending.reject`, но если ответ уже отдан стримом (после `http-response-start`), промис resolved и reject — no-op; `controller.error()` не вызывается, entry удаляется из map → браузерный ответ висит вечно (пост-start таймаута нет, `startTimeout` очищен при resolve). relay-client реально шлёт error-фрейм посреди стрима, если чтение локального body упало (`relay-client.ts:241-249`). Для сравнения: `closePendingRequestsForDispatcher` (`relay-server.ts:398-406`) делает это правильно через `controller.error()`.

Фикс: в case `http-response-error` — если `pending.controller` есть, звать `controller.error(...)`, иначе `reject`.

### E2. `thread-follower-edit-last-user-turn` не поддержан для dispatcher-owned тредов — DONE

Метод есть в `followerRequestMethods` (`server.ts:81`) и в мостах webview (`extension-webview.ts:68`, `:101-103`), но отсутствует в `dispatcherOwnerRequestMethods` (`server.ts:90-103`) и в switch `handleDispatcherOwnerRequest` — dispatcher не регистрирует IPC-хендлер для него. VS Code-follower, редактирующий последний user turn на dispatcher-owned треде, получит `no-handler-for-request`/`no-client-found`. (Примечание: ревьюер описал механизм неверно — метода нет в set вообще, а не «нет case в switch»; проверено grep'ом. Функциональный пробел реальный. Смягчение: подсистема сейчас дремлет, см. E3.)

Сделано (после E3 подсистема больше не дремлет, так что пробел стал достижимым): метод добавлен в `dispatcherOwnerRequestMethods` и реализован по семантике настоящего owner'а, вычитанной из бандла экстеншна — проверить, что правится именно последний turn и он не in-progress, `thread/rollback` на один turn, затем `turn/start` с тем же input'ом, где текст заменён на новый. Отличие от экстеншна вынужденное и явное: он берёт input из своей in-memory модели треда (`turn.params.input`), а у нас есть только то, что отдаёт `thread/read` — turn как список items. Поэтому input пересобирается из `userMessage.content`, а редактирование сообщения с нетекстовыми частями (аттачи) отвергается явной ошибкой вместо тихой потери вложений.

Проверено на живом стенде: «телефон» стартует тред и turn («reply with the single word: alpha»), сторонний Codex IPC клиент в роли VS Code шлёт `thread-follower-edit-last-user-turn` с новым текстом → диспетчер откатывает и перезапускает turn, снапшот у пира содержит один turn с отредактированным сообщением и ответом «beta».

### E3. Blast radius B1: вся dispatcher-owner подсистема мертва — DONE

`dispatcherOwnedConversations` пополняется только из WS-путей legacy UI (`server.ts:330, 349, 383, 412` → `:519, 709, 718`), которые недостижимы (B1). Треды, стартованные из webview, идут через `mcp-request` → `thread/start` напрямую и owner'ом не помечаются. Значит `handleDispatcherOwnerRequest`, `scheduleDispatcherOwnedRefresh`, replay owned-снапшотов (`server.ts:796-804`) и `dispatcher-owner.ts` сейчас не активируются — заявленный в TASKS.md пункт 3 «Dispatcher owner mode — done» фактически не работает через актуальный UI. Решение по B1 обязано включать судьбу этой подсистемы (~300+ строк сверх legacy UI): либо помечать webview-стартованные треды owner'ами, либо резать.

Решение пользователя: оживить. Сделано: каждое окно VS Code поднимает свой app-server, поэтому turn, стримящийся на *нашем* — это turn, который ведёт диспетчер. Отсюда правило владения: тред, по которому webview что-то сделал через наш app-server, становится dispatcher-owned (`onThreadActivity` из `handleMcpRequest` плюс claim по notification'ам), кроме тредов, владение которыми уже объявило окно VS Code (`streamOwners`). `thread/start` сажает состояние прямо из результата запроса — читать его обратно нельзя, app-server отказывается отдавать turns до первого user-сообщения.

Проверено на живом стенде (реальный `codex app-server`, диспетчер на :8799, второй Codex IPC клиент в роли VS Code): тред, стартованный «телефоном», отдаёт роль `owner` (незнакомый — `follower`), пир получил 7 снапшотов `thread-stream-state-changed` с `hostId: local` за один turn, последний — с готовым turn'ом.

Правки после ревью: (1) владение теперь **отпускается** — снапшот `thread-stream-state-changed` от чужого clientId означает, что окно VS Code взялось вести тред, и диспетчер снимает свою запись (двое владельцев гнали бы параллельные turn'ы по одному rollout и мигали бы follower'ам двумя состояниями). Это же закрывает пористость guard'а `streamOwners`: если мы забрали тред ошибочно (диспетчер подключился к IPC посреди чужого стрима, IPC-реконнект стёр владельцев), первый же чужой снапшот вернёт владение. (2) Claim сузился до методов, которые тред реально *ведут* (`thread/start|resume|fork|compact/start|rollback`, `turn/start|steer|interrupt`): раньше любой `thread/read` или архивация чужого треда делали диспетчер его вечным владельцем.

Живая проверка попутно вскрыла две реальные дыры: (1) `void refreshDispatcherOwnedConversation(...)` роняло весь диспетчер unhandled rejection'ом, когда `thread/read` возвращал ошибку — теперь падение ловится на границе таймера и логируется; (2) refresh по notification'у для только что созданного треда всегда упирался в «not materialized yet», поэтому notification-путь обновляет только треды, у которых уже есть turns (turn, отправленный вебвью, обновляет безусловно — это и есть момент материализации).

### E4. Нарушение инварианта «один webview»: несколько вкладок/устройств

VS Code гарантирует один webview-инстанс; в бридже каждая вкладка — полноценный клиент. `mcp-request` (аппрувы) броадкастится всем SSE-клиентам (`extension-webview.ts:218-228`), а ответить может каждая вкладка: второй `respondToServerRequest` кидает «No pending app-server request» (`codex-app-server.ts:160`) → host-message-error 500 во второй вкладке. Плюс дрейф состояния между вкладками (ответы на host-запросы видит только запросившая вкладка). Нужно решение: либо single-active-client (остальные read-only/kick), либо дедупликация ответов на server requests.

### E5. Асимметрия типов id в mcp-мостах — DONE

`handleMcpRequest` требует строковый `request.id` (`extension-webview.ts:595`), `handleMcpResponse` принимает string|number (`:667`). Числовой id запроса от экстеншна даст «Invalid mcp-request payload». Унифицировать.
