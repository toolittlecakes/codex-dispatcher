## A. Fidelity бриджа к VS Code host (высокий приоритет)

### A1. Два несинхронизированных канала доставки сообщений в webview — DONE

В VS Code webview↔host — один упорядоченный FIFO-канал `postMessage`. В бридже два: ответы на host-message приходят в POST response (`deliver(body.messages)` в shim, `extension-webview.ts:986-1005`), broadcast'ы — через SSE (`:1023`). Плюс каждый `postMessage` из webview — отдельный параллельный fetch: порядок обработки на сервере и порядок доставки ответов не гарантирован. Симптом: редкие гонки состояния/стрима, которых нет в VS Code (notification о turn приходит раньше ответа на запрос, который его запустил, и т.п.).

Направление фикса: один упорядоченный канал (например, весь трафик через один WebSocket с seq-номерами) либо очередь на клиенте (сериализовать `sendHostMessage`) + доставка ответов через тот же SSE-поток, чтобы сервер контролировал порядок.

Сделано (host→webview): POST `/host-message` больше не возвращает сообщения — только `{ accepted: true }`. Все исходящие сообщения (и ответы, и broadcast'ы) идут одним потоком с общей seq-нумерацией, поэтому порядок доставки задаёт сервер, а не гонка параллельных fetch'ей. Шим генерирует `clientId` (`crypto.randomUUID`), передаёт его в `x-dispatcher-client` на POST и в `?client=` на `/events` — так ответ попадает именно в поток той вкладки, которая спросила, а не «куда-нибудь». Буфер/`Last-Event-ID` из A2 стали per-client: `StreamClient { seq, buffer, controller, detachedAt }`; отсоединённые клиенты держатся 5 минут (чтобы пережить блокировку экрана) и потом собираются `pruneDetachedClients`. Побочный эффект, соответствующий реальному хосту: инициатор `persisted-atom-update` теперь тоже получает `persisted-atom-updated` — в VS Code экстеншн так же постит в webview, из которого пришло обновление.

**Правки после ревью (три регрессии/дыры первой версии):** (1) гонка «POST раньше первого `/events`» — EventSource подключается асинхронно, вебвью успевает спросить до открытия потока, ответ буферизовался, а свежее подключение без `Last-Event-ID` буфер игнорировало и слало resync — ответ терялся навсегда. Теперь подключение без `Last-Event-ID` при нетронутом буфере (первый элемент всё ещё `id: 1`) проигрывает буфер целиком: «не видел ни одного события» + «ничего не вытеснено» = буфер и есть ровно пропущенное. (2) `cancel` мёртвого сокета срабатывает уже после реконнекта и убивал *новый* живой поток (обнулял controller и heartbeat) — вкладка немела до перезагрузки; теперь `detachIfCurrent` рвёт клиента только по тому controller'у, который сейчас привязан. (3) вкладка, которая сделала POST и больше никогда не открывала `/events`, не собиралась никогда: `pruneDetachedClients` звался только при открытии потока. Добавлен prune в `broadcast` — единственное место, куда мы ещё попадаем после закрытия вкладки. Не принято из ревью: «resync-фреймы делят один event id» — это намеренно, id на снапшоте означает текущую позицию потока, чтобы реконнект после resync не запросил повтор уже пересланного.

Сделано (webview→host): вторая половина канала. Раньше каждый `postMessage` был отдельным параллельным `fetch` — порядок прибытия задавала сеть. Теперь у шима один outbox и ровно один запрос в полёте: пока он летит, сообщения копятся и уходят следующим батчем (`{ messages: [...] }`), так что порядок отправки == порядок прибытия, а всплеск на бутстрапе не превращается в цепочку последовательных round-trip'ов. На хосте POST больше не ждёт обработку: сообщения батча *стартуют* по порядку (`dispatchHostMessage` без await) и отвечают когда ответят — это и есть семантика VS Code, где handler вызывается строго по порядку, но канал не блокируется на его async-работе. Если бы POST ждал обработку, один внешний fetch (до 25s) вешал бы весь канал. Следствие: `{ accepted: true }` означает «принято к обработке», ошибки приходят в поток как `host-message-error`.

**Вторая итерация ревью — ещё три дыры.** (1) Реплей буфера на свежем подключении *заменял* resync-снапшот вместо того, чтобы дополнять его: в том же окне гонки вкладка получала свои ответы, но теряла pending approvals (без них turn стоит без промпта). Теперь буфер и resync идут вместе, буфер первым (он старее), resync последним как актуальное состояние; ранний `return` остался только для настоящего resume. (2) Нумерация событий живёт внутри одной инкарнации клиента, а браузер помнит `Last-Event-ID` через prune клиента (вкладка в фоне >5 мин) и через рестарт диспетчера: старый id либо уводил в resync с потерей уже забуференных ответов, либо (если старый id < нового seq) молча выкидывал начало новой нумерации. Теперь у клиента есть `epoch`, event id — `epoch.seq`, и resume принимается только при совпадении epoch, иначе это свежий поток. (3) Шим не смотрел на HTTP-статус ответа `/host-message` — батч из N сообщений мог исчезнуть без следа (400 от старой вкладки после апгрейда, 401 по протухшей cookie); теперь не-2xx поднимает ошибку по каждому сообщению батча. Плюс сериализация теперь по одному сообщению, чтобы несериализуемое значение роняло только себя, как `postMessage` в VS Code, а не соседей по батчу. Ответ на битый батч больше не притворяется `fetch-response` с `requestId: undefined` — это `host-message-error`.

**Третья итерация ревью.** (1) `pruneDetachedClients` звался *после* `clientFor` — вкладка, проспавшая больше 5 минут, переподключалась к записи, которую тут же удаляли из мапы: стрим жив, heartbeat идёт (браузер не видит обрыва), но broadcast'ы её не находят, а следующий POST заводит новую запись — молчаливый вечный столл. Prune теперь идёт первым, стухшая запись честно умирает и вкладка получает свежий поток с resync. (2) Все сообщения resync уходили с одним id (seq не рос), поэтому обрыв в середине снапшота был неотличим от «получил весь снапшот»: реконнект по этому id возвращал пустой diff и хвост (в т.ч. pending approvals) терялся навсегда. Теперь resync идёт через обычный `send` — со своими номерами и в буфере, так что обрыв посреди снапшота нормально доигрывается. (3) `JSON.stringify` возвращает `undefined` (а не бросает) для `undefined`/функции/символа — такое сообщение делало тело батча невалидным JSON и топило соседей; теперь шим бросает сразу у вызывающего, как `postMessage` в VS Code роняет только своего caller'а.

Известная дыра покрытия: сам шим — инлайновая строка, юнит-тестами недостижим (проверка `response.ok`, outbox, сборка тела). Тестируется только серверная половина канала.

Попутно починен тестовый хелпер `openEventStream`: брошенный по таймауту `reader.read()` всё равно съедал следующий чанк, и события молча терялись — теперь один read держится в полёте между итерациями опроса.

### A2. Потеря событий при SSE reconnect — DONE

EventSource авто-реконнектится, но нет Last-Event-ID/буфера: всё, что broadcast'нулось во время разрыва (блокировка телефона убивает соединение), теряется. Replay при реконнекте (`buildExtensionEventReplayMessages`, `server.ts:781`) отдаёт только thread-stream снапшоты; `mcp-notification` и `mcp-request` (pending approvals!) от app-server не реплеятся — тихая потеря. Дополнительно: шим не вешает `events.onerror` — перманентная смерть SSE-соединения тоже тихая для пользователя.

Сделано: каждое исходящее SSE-сообщение получает монотонный `id`, последние 500 держатся в ring-buffer'е, а реконнект с `Last-Event-ID` догоняет ровно пропущенное. Если разрыв не покрывается буфером (или id вне диапазона) — явный полный resync из текущего состояния. В replay добавлены pending server requests (аппрувы/элиситации), иначе после реконнекта turn стоял бы без промпта. Шим получил `events.onerror`, чтобы смерть стрима перестала быть неотличимой от тишины.

### A3. `handleMcpResponse` выбрасывает error из ответа webview — DONE

`extension-webview.ts:670`: `respondToServerRequest(String(response.id), response.result ?? null)` — если webview ответил на server request с `error`, app-server получает успешный `result: null`. Молчаливое искажение. `CodexAppServer.respondToServerRequest` вообще не умеет передавать error.

Фикс: пробрасывать `error` в JSON-RPC ответ app-server'у.

### A4. `handleExternalFetch` не эквивалентен настоящему fetch — DONE

- При `!response.ok` тело ответа выбрасывается, возвращается error со `statusText` (`extension-webview.ts:1262`). Реальный fetch отдаёт body и на 4xx/5xx; экстеншн может парсить JSON ошибки.
- Жёсткий `AbortSignal.timeout(10_000)` на все внешние запросы — долгие запросы отваливаются.
- Полная буферизация ответа — стриминговые ответы не работают.

Контракт подтверждён по бандлу экстеншна (`onFetchResponse`, `openai.chatgpt-26.803.61601`): при `responseType: "success"` вебвью резолвит 2xx через `JSON.parse(bodyJsonString)`, а любой другой статус реджектит как `new Pd(bodyJsonString, status)` — т.е. тело non-2xx ответа и есть текст ошибки. `responseType: "error"` (с опциональным `errorCode`) предназначен для несостоявшегося обмена.

Сделано: любой завершившийся HTTP-обмен возвращается как `success` с реальным статусом и телом (`readExternalFetchBody`); `error` остался только для транспортных сбоев. По стримингу решение зафиксировано: host-стриминг не нужен — `fetch-stream-*` сообщения генерирует websocket-путь внутри самого вебвью, а контракт `fetch` — строго request/response.

**Осознанное отклонение от реального host (уточнено ревью):** настоящий VS Code host в `out/extension.js` тоже отдаёт non-2xx как `responseType: "error"` со `statusText` и тело выбрасывает. Наш вариант остаётся внутри того же контракта вебвью, но даёт строго более информативный reject (тело вместо `statusText`) — отклонение намеренное и зафиксировано здесь, а не случайное.

**Таймаут — правка после ревью.** Первая версия подняла таймаут 10s → 120s и этим сломала relay-путь: `fetch-response` едет в теле POST `/host-message`, relay сдаётся через 30s (`startTimeout`) и шлёт `http-request-cancel`, а вебвью settle'ит pending fetch только по приходу `fetch-response` — в окне 30–120s промис висел бы вечно. Раньше инвариант `host < relay` держался случайно (10s < 30s). Итог: таймаут 25s, ниже самого строгого звена цепочки (relay `startTimeout` 30s, Bun `idleTimeout` 60s), инвариант зафиксирован комментарием в коде. Развязать это ограничение может только A1 (унести `fetch-response` из тела POST в общий поток).

**Follow-up (pre-existing, не блокер):** реальный host на 401 делает token-refresh и backoff-ретраи retryable-статусов — эмуляция этого не делает, так что 401 долетает до вебвью как reject вместо тихого рефреша.

### A5. Version coupling с экстеншном без контракта — DONE

Бридж жёстко завязан на контракт конкретной версии экстеншна: списки `vscode://codex/*` endpoints (`handleVSCodeRequest`), follower-методы, `methodVersions` (`thread-stream-state-changed: 6`, захардкожен также в `server.ts:801`), wham/statsig стабы. При этом `resolveExtensionWebviewRoot` берёт последнюю установленную версию экстеншна — автообновление ломает бридж молча (`Unsupported vscode://codex/...`). Уже копятся version-specific хаки: strip `workspace_dependencies` (`extension-webview.ts:1397`), кэш `experimentalFeature/enablement/set` (`:627`). Мелочь рядом: `extensionVersion()` (`extension-webview.ts:1611`) пересканирует диск и может разойтись с `webviewRoot`, зарезолвленным при старте.

Фикс: пиннинг поддерживаемой версии экстеншна (диапазон) с явной ошибкой при несовпадении + smoke/contract-тест против реально установленной версии.

Сделано: диапазон поддерживаемых версий зафиксирован в коде (`supportedExtensionVersions`, сейчас 26.422.x — 26.803.x: нижняя граница — версия, против которой делался UI-parity, верхняя — последняя проверенная end-to-end). Автодискавери больше не берёт «просто самую свежую установленную», а выбирает самую свежую *поддерживаемую*; если установлены только версии вне диапазона — явная ошибка с перечислением найденного вместо молчаливого `Unsupported vscode://codex/...` где-то в середине сессии. `doctor` показывает это как FAIL с текстом ошибки, а не падает. Явный `CODEX_EXTENSION_WEBVIEW_ROOT` остаётся способом сказать «знаю, что делаю» — версионная проверка к нему не применяется. Сканирование вынесено в чистую `selectExtensionWebviewRoot(extensionsDir)`, поэтому выбор версии тестируется на настоящей файловой системе, а не на моках; отдельный smoke-тест падает, если экстеншн, реально установленный на машине, вышел за диапазон. Правки после ревью: `serve --install-extension` на чистой машине ставил marketplace latest, который пиннинг тут же отверг бы — теперь ставится ровно проверенная версия (`openai.chatgpt@26.803.61601`), и `doctor` пишет её же. И убран тихий fall-through: `CODEX_EXTENSION_WEBVIEW_ROOT` с опечаткой раньше молча игнорировался и уходил в автоскан (оператор ставил override именно чтобы запустить unsupported-версию — и получал ошибку про неподдерживаемую версию), теперь это явная ошибка про отсутствующий `index.html`. Заодно `extension-info` больше не пересканирует диск: версия выводится из уже зарезолвленного `webviewRoot` (`extensionVersionOf`), так что разойтись они больше не могут.

### A6. Debounce вместо throttle в `scheduleDispatcherOwnedRefresh` — DONE

`server.ts:723`: каждый notification ресетит 120ms таймер. При стриме чаще 120ms refresh откладывается до паузы — starvation: VS Code-follower dispatcher-owned треда видит фриз, потом скачок. Поправка по итогам ревью: `dispatcherOwnedConversations` наполняется только из мёртвого WS-протокола (см. B1/E3), так что симптом сейчас недостижим — чинить вместе с решением по E3.

Фикс: trailing throttle (гарантированный refresh не реже, чем раз в N ms), не debounce.

Сделано вместе с E3 (подсистема ожила, значит starvation стал достижим): первый notification ставит таймер, последующие в окне его не сдвигают, `delayMs = 0` (аппрувы) по-прежнему вытесняет отложенный refresh. На живом прогоне один turn дал 7 снапшотов вместо одного в конце.

## B. Мёртвый код

### B1. `canHandle` всегда true → `public/` и WS-протокол недостижимы — DONE

`extension-webview.ts:168`: `canHandle` = `pathname.startsWith("/")` — всегда true. Следствия:

- `serveStatic` и весь `public/` (legacy UI: `app.js`, `index.html`, `styles.css`, `sw.js`, `manifest.webmanifest`, `approval-requests.js`) не отдаются никогда. Исключение — `json-patch.js`, который сервер импортирует напрямую.
- PWA manifest и service worker не отдаются: если PWA-установка заявлена как фича — она сломана.
- Почти весь WS-протокол `ClientMessage` в `server.ts` (~400 строк: listThreads/startTurn/rotateToken/...) обслуживает мёртвый UI.

Решение нужно явное: либо выпилить legacy UI + мёртвую часть WS-протокола (и перенести `json-patch.js` в `src/`), либо это баг routing'а и PWA-ассеты надо начать отдавать. Blast radius больше, чем кажется: вместе с WS-протоколом мертва вся dispatcher-owner подсистема — см. E3.

Сделано (решение пользователя: выпилить UI, PWA сделать по-настоящему). Удалены `public/`, `serveStatic`, `/ws` и весь `ClientMessage`-протокол вместе с осиротевшими хелперами (`securitySnapshot`, `broadcastSecurity`, `markDispatcherOwner*`, `ensureDispatcherOwnedConversation`, `scheduleRefreshForServerRequest`); `json-patch` переехал в `src/json-patch.ts` с типами (закрывает D2). `DISPATCHER_REMOTE_URL` больше некому читать — убран и из `cli.ts`. stderr app-server'а и IPC писались только в мёртвый UI — теперь идут в консоль.

PWA сделан на поверхности вебвью (`src/pwa.ts`): `/manifest.webmanifest`, `/sw.js` и `/icon.png` (иконка берётся из самого расширения, 385x385) отдаются без токена — браузер тянет манифест без нашей куки; в `<head>` инжектятся link'и, apple-touch-icon и регистрация worker'а. Worker намеренно ничего не кэширует (кэш отдавал бы ассеты версии расширения, которую диспетчер больше не хостит) — только `fetch`-listener ради installability. Кука сессии получила `Max-Age`, иначе установленное приложение стартовало бы с `start_url` в 401. Проверено живьём: манифест/worker/иконка отдаются анонимно, `/` без токена — 401, `/ws` — 404.

### E6. `dispatcherOwnedConversations` растёт монотонно (найдено ревью E3) — DONE

Записи владения не удаляются ни по какому таймауту: удаление есть только при передаче владения окну VS Code (`releaseDispatcherOwnership`). Каждая запись после refresh держит полные turns; `client-status-changed: connected` рассылает снапшоты по всем накопленным тредам, а `buildExtensionEventReplayMessages` реплеит их все каждому подключающемуся webview. В долгоживущем процессе память и объём реплея растут с каждым тредом, который телефон когда-либо вёл.

Решение по указанию пользователя: «изучи, как это в VS Code, и сделай так же». Изучено по бандлу расширения (`out/extension.js`) и по webview-бандлу (`webview/assets/app-initial-CM3BD-Et.js`, класс координации стримов). Модель там такая:

- broadcast'ы IPC поддерживают адресацию: `targetClientIds`. Роутер фильтрует получателей, клиент на приёме фильтрует ещё раз (`if(e.targetClientIds!=null&&!e.targetClientIds.includes(this.clientId))return`), а отправитель с пустым списком не шлёт ничего (`if(n?.length===0)return`);
- владелец треда держит `followerClientIdsByConversationId` и шлёт снапшоты/патчи **только** тем, кто заявил, что следит: `broadcastConversationSnapshot`/`broadcastIpcStatePatches` выходят сразу, если множество пустое. Никакой рассылки «всем и по всем тредам» не существует;
- follower объявляет интерес broadcast'ом `thread-stream-following-changed {conversationId, hostId, following}`. На `following:true` владелец сразу шлёт снапшот именно этому клиенту;
- владелец, взявший тред и не знающий followers, шлёт `thread-stream-following-status-requested`, и каждый клиент, у которого этот тред открыт, отвечает `thread-stream-following-changed` в его адрес;
- при подключении нового клиента follower'ы переобъявляют свои подписки (`client-status-changed: connected`), при отключении клиента владелец вычищает его из всех множеств, при `ipc-connection-reset` — очищает все.

Сделано ровно это. `codex-ipc.ts`: `targetClientIds` в типе broadcast'а, фильтрация в роутере и на приёме у клиента, пустой список = не слать (тесты `tests/codex-ipc.test.ts` поднимают настоящий роутер и три клиента на временном сокете). `server.ts`: `streamFollowersByConversation`, обработка `thread-stream-following-changed` (парсер — чистая функция в `dispatcher-owner.ts`, проверяет `hostId`), снапшот адресуется followers и не отправляется вовсе, когда их нет, `thread-stream-following-status-requested` при взятии владения, чистка при disconnect'е клиента, при передаче владения и при обрыве IPC. Рассылка «все снапшоты на каждый connect» удалена — followers сами переобъявляются.

Реплей owned-тредов в свой webview убран из `buildExtensionEventReplayMessages`: webview ведёт эти треды через наш app-server и уже знает их состояние, а реплей рос с каждым когда-либо запущенным тредом. Эвикшн самого `dispatcherOwnedConversations` не добавлен намеренно: в VS Code владелец тоже держит стейт треда всю сессию, а любой TTL/LRU — это молчаливая потеря владения под носом у follower'а (то, из-за чего пункт и не был решён раньше). Теперь размер этой карты не создаёт трафика: нет followers — нет отправок.

Не проверено живьём с настоящим окном VS Code в роли follower'а (нужен второй хост и живой тред): проверены загрузка диспетчера с новой веткой IPC и адресация на настоящем сокете в тестах.

Побочно в том же коммите: сокет для проверки «есть ли роутер» и для подключения теперь создаётся через `new Socket()` с обработчиками до `connect`. **Уточнение после ревью:** заявленный в сообщении коммита «синхронный ENOENT в Bun» верен не в общем виде — отдельным скриптом с `net.connect(path, cb)` ошибка приходит асинхронно и поздний листенер её ловит. Синхронно она пришла в связке, которая реально падала (метод `socket.connect(path, cb)` под `bun test`: исключение проходит наружу через `canConnectToSocket` → `startRouterIfNeeded` → `start()` уводит бридж в error+reconnect, роутер не поднимается). Порядок «слушатели до соединения» безопасен в обоих случаях, но это защита, а не подтверждённый продакшн-баг.

**Правки после ревью коммита b53610b.** Ревьюер нашёл, что реализована только владельческая половина протокола, и это ломает передачу владения: раньше мы видели чужие снапшоты случайно (наш роутер не фильтровал), а теперь адресные кадры до нас не доходят вообще, поэтому окно VS Code, забравшее тред, осталось бы незамеченным — два владельца на одном rollout. Сделана follower-половина, как в бандле:

- диспетчер объявляет following на все треды, состояние которых у него есть (owned + mirrored) — это его аналог «открытых в окне тредов»;
- на входящий `thread-stream-following-status-requested` по нашему хосту он отвечает `thread-stream-following-changed{following:true}` в адрес спрашивающего; снапшот нового владельца затем приходит и снимает наше владение существующим путём (единственный триггер release не размножен);
- на `client-status-changed: connected` от чужого клиента — объявление following в его адрес (он ещё не знает наш id);
- при регистрации нашего клиента (новый clientId после реконнекта) — переобъявление following по всем тредам и повторный `thread-stream-following-status-requested` по owned. Это же закрывает потерю запроса, отправленного при `claim`, когда IPC ещё не подключён;
- пустые множества followers удаляются из map при disconnect'е клиента.

Тест на фильтрацию в самом роутере добавлен отдельно: подключается «сырой» клиент прямо по фрейм-протоколу, потому что через `CodexIpcBridge` дырявый роутер маскируется приёмным фильтром (проверено: без фильтра в роутере тест падает).

### E7. Пересекающиеся refresh'ы owned-треда (найдено ревью E3) — DONE

`scheduleDispatcherOwnedRefresh` удаляет таймер из map до `await thread/read`, поэтому второй refresh может стартовать, пока первый в полёте; при завершении не в порядке отправки старый снапшот перезапишет более новый. Самолечится следующим событием треда. Не проверено, гарантирует ли app-server порядок ответов.

Порядок проверен на настоящем `codex app-server`: два конкурентных `thread/list` (limit 100, затем limit 1) завершились в обратном порядке отправки — ответы приходят по мере готовности, гарантии порядка нет. Значит гонка настоящая, а не теоретическая: при живом turn'е refresh по throttle-таймеру и немедленный refresh (`delayMs: 0` из notification'а/аппрува) регулярно пересекаются.

Сделано: одна операция чтения на тред одновременно. Пока `thread/read` в полёте, повторный запрос не стартует второй, а поднимает флаг; по завершении первого — один перезапуск через тот же таймер (`scheduleDispatcherOwnedRefresh(threadId, 0)`), чтобы ошибка чтения по-прежнему обрабатывалась на единственной границе, которая её ловит и логирует. Флаг снимается и при передаче владения.

Автотеста нет: логика живёт в `server.ts`, а это скрипт с побочными эффектами на верхнем уровне (стартует app-server, IPC и HTTP при импорте) — его нельзя импортировать в тест. Проверено чтением и живым замером порядка ответов выше.

Правка после ревью: владение перепроверяется **после** `await thread/read`, а не только до него. Тот же класс stale-write: пока чтение в полёте, снапшот от окна VS Code мог снять с нас владение, а запись ответа возвращала тред в `dispatcherOwnedConversations` — и диспетчер снова начинал принимать follower-запросы по треду, который уже ведёт другое окно.

Известная граница (не чинится намеренно): если `thread/read` зависнет — app-server жив, но не отвечает, — флаг in-flight не снимется и refresh'ы этого треда прекратятся молча. Таймаута на запросы к app-server нет и вводить его нельзя огулом: через тот же `request` идут turn'ы, которые легально длятся минутами. До правки зависший запрос терял один refresh, теперь — все последующие по этому треду; сценарий требует живого-но-молчащего app-server, у которого и без того ничего не стримится.

## C. Security

### C1. Relay: response-фреймы не привязаны к сессии отправителя — DONE

### C3. Мелочи — DONE

- Сравнение dispatcher-токена не constant-time (`extension-webview.ts:240-247`, а также `/ws` в `server.ts:199`) — заменить на `crypto.timingSafeEqual`.
- Кука дispatcher'а без `Secure`/`Max-Age` (`authCookie`, `extension-webview.ts:1658`). Нюанс: локальный сценарий — http по LAN, `Secure` там сломает вход; ставить флаг только когда запрос пришёл через relay/https.
- **Коллизия имён кук — повышена по итогам ревью, достижима.** Имя `codex_dispatcher_session` совпадает у relay (Domain-кука на `.codex-dispatcher.app`, `relay-server.ts:496`) и дispatcher'а (`extension-webview.ts:54`). Если пользователь откроет через relay URL с `?token=` (dispatcher отдаст свой `set-cookie` в `serveIndex`, `extension-webview.ts:263-265`), браузер получит две одноимённые куки, и `cookieValue` relay (`relay-server.ts:507`) возьмёт первую попавшуюся → ломается relay-авторизация. Переименовать одну из кук.

Сделано: все три сравнения токена (query, `x-dispatcher-token`, кука) идут через `timingSafeEqual` с проверкой длины; `/ws` уехал вместе с B1. Кука диспетчера переименована в `codex_dispatcher_webview` (переименован именно диспетчер, а не relay: смена имени relay-куки разлогинила бы всех). `Secure` ставится, когда запрос пришёл по https — relay терминирует TLS и форвардит по loopback, поэтому он теперь проставляет `x-forwarded-proto` сам, перезаписывая клиентский. `Max-Age` добавлен ещё в B1/PWA. Проверено живьём: по http куки без `Secure`, с `x-forwarded-proto: https` — с `Secure`, обрезанный токен даёт 401, кука с новым именем — 200.

Правки после ревью: (1) `secretEquals` сравнивал длину в UTF-16 code units, а `timingSafeEqual` — байты, поэтому кандидат из multibyte-символов нужной длины кидал `RangeError` вместо 401 (регрессия, внесённая этим же коммитом; воспроизведено) — длина считается в байтах. (2) Relay читал первую попавшуюся куку с нужным именем, из-за чего браузер с оставшейся от старого бага host-only `codex_dispatcher_session` попадал в цикл логина; `cookieValues` теперь возвращает все значения, relay аутентифицируется по любому подходящему, а нераскодируемая кука пропускается вместо 500 (заодно pre-existing `URIError` в relay).

### C4. Токен диспетчера не переживает рестарт (найдено ревью B1) — DONE (решение: PWA только через relay)

`cli.ts:90` и `server.ts:17` генерируют новый `DISPATCHER_TOKEN` на каждый запуск и никуда его не пишут. Для relay-пути это неважно: `relay-client.ts:205` подставляет актуальный токен в каждый форварженный запрос, а телефон авторизуется relay-сессией. Но на LAN/tunnel установленное на домашний экран приложение открывает `start_url: "/"` без токена, и после рестарта диспетчера кука (теперь с `Max-Age`) становится невалидной: на Android лечится открытием свежей token-ссылки (общий cookie jar с браузером), на iOS у home-screen приложения изолированное хранилище и нет адресной строки — только переустановка. Решение пользователя: **устанавливать PWA только через relay**; LAN-установка на домашний экран не поддерживается. Кода не требуется — на relay-пути токен диспетчера не участвует в аутентификации браузера (`relay-client.ts` подставляет актуальный токен в каждый форварженный запрос, телефон держит relay-сессию), поэтому рестарт диспетчера установленное приложение не ломает. Токен намеренно остаётся эфемерным: персистить секрет в файл ради неподдерживаемого сценария — лишняя поверхность. LAN-ссылка с `?token=` остаётся тем, чем была, — способом открыть вебвью в браузере, а не установить приложение.

## E. Добавлено по итогам ревью субагентом (пропущено в первом проходе)

### E1. Relay: `http-response-error` после `http-response-start` вешает браузерный стрим — DONE

`relay-server.ts:373-381`: при error-фрейме вызывается `pending.reject`, но если ответ уже отдан стримом (после `http-response-start`), промис resolved и reject — no-op; `controller.error()` не вызывается, entry удаляется из map → браузерный ответ висит вечно (пост-start таймаута нет, `startTimeout` очищен при resolve). relay-client реально шлёт error-фрейм посреди стрима, если чтение локального body упало (`relay-client.ts:241-249`). Для сравнения: `closePendingRequestsForDispatcher` (`relay-server.ts:398-406`) делает это правильно через `controller.error()`.

Фикс: в case `http-response-error` — если `pending.controller` есть, звать `controller.error(...)`, иначе `reject`.

### E2. `thread-follower-edit-last-user-turn` не поддержан для dispatcher-owned тредов — DONE

Метод есть в `followerRequestMethods` (`server.ts:81`) и в мостах webview (`extension-webview.ts:68`, `:101-103`), но отсутствует в `dispatcherOwnerRequestMethods` (`server.ts:90-103`) и в switch `handleDispatcherOwnerRequest` — dispatcher не регистрирует IPC-хендлер для него. VS Code-follower, редактирующий последний user turn на dispatcher-owned треде, получит `no-handler-for-request`/`no-client-found`. (Примечание: ревьюер описал механизм неверно — метода нет в set вообще, а не «нет case в switch»; проверено grep'ом. Функциональный пробел реальный. Смягчение: подсистема сейчас дремлет, см. E3.)

Сделано (после E3 подсистема больше не дремлет, так что пробел стал достижимым): метод добавлен в `dispatcherOwnerRequestMethods` и реализован по семантике настоящего owner'а, вычитанной из бандла экстеншна — проверить, что правится именно последний turn и он не in-progress, `thread/rollback` на один turn, затем `turn/start` с тем же input'ом, где текст заменён на новый. Отличие от экстеншна вынужденное и явное: он берёт input из своей in-memory модели треда (`turn.params.input`), а у нас есть только то, что отдаёт `thread/read` — turn как список items. Поэтому input пересобирается из `userMessage.content`, а редактирование сообщения с нетекстовыми частями (аттачи) отвергается явной ошибкой вместо тихой потери вложений.

Проверено на живом стенде: «телефон» стартует тред и turn («reply with the single word: alpha»), сторонний Codex IPC клиент в роли VS Code шлёт `thread-follower-edit-last-user-turn` с новым текстом → диспетчер откатывает и перезапускает turn, снапшот у пира содержит один turn с отредактированным сообщением и ответом «beta».

### E3. Blast radius B1: вся dispatcher-owner подсистема мертва — DONE

`dispatcherOwnedConversations` пополняется только из WS-путей legacy UI (`server.ts:330, 349, 383, 412` → `:519, 709, 718`), которые недостижимы (B1). Треды, стартованные из webview, идут через `mcp-request` → `thread/start` напрямую и owner'ом не помечаются. Значит `handleDispatcherOwnerRequest`, `scheduleDispatcherOwnedRefresh`, replay owned-снапшотов (`server.ts:796-804`) и `dispatcher-owner.ts` сейчас не активируются — заявленный в TASKS.md пункт 3 «Dispatcher owner mode — done» фактически не работает через актуальный UI. Решение по B1 обязано включать судьбу этой подсистемы (~300+ строк сверх legacy UI): либо помечать webview-стартованные треды owner'ами, либо резать.

Решение пользователя: оживить. Сделано: каждое окно VS Code поднимает свой app-server, поэтому turn, стримящийся на *нашем* — это turn, который ведёт диспетчер. Отсюда правило владения: тред, по которому webview что-то сделал через наш app-server, становится dispatcher-owned (`onThreadActivity` из `handleMcpRequest` плюс claim по notification'ам), кроме тредов, владение которыми уже объявило окно VS Code (`streamOwners`). `thread/start` сажает состояние прямо из результата запроса — читать его обратно нельзя, app-server отказывается отдавать turns до первого user-сообщения.

Проверено на живом стенде (реальный `codex app-server`, диспетчер на :8799, второй Codex IPC клиент в роли VS Code): тред, стартованный «телефоном», отдаёт роль `owner` (незнакомый — `follower`), пир получил 7 снапшотов `thread-stream-state-changed` с `hostId: local` за один turn, последний — с готовым turn'ом.

Правки после ревью: (1) владение теперь **отпускается** — снапшот `thread-stream-state-changed` от чужого clientId означает, что окно VS Code взялось вести тред, и диспетчер снимает свою запись (двое владельцев гнали бы параллельные turn'ы по одному rollout и мигали бы follower'ам двумя состояниями). Это же закрывает пористость guard'а `streamOwners`: если мы забрали тред ошибочно (диспетчер подключился к IPC посреди чужого стрима, IPC-реконнект стёр владельцев), первый же чужой снапшот вернёт владение. (2) Claim сузился до методов, которые тред реально *ведут* (`thread/start|resume|fork|compact/start|rollback`, `turn/start|steer|interrupt`): раньше любой `thread/read` или архивация чужого треда делали диспетчер его вечным владельцем.

Живая проверка попутно вскрыла две реальные дыры: (1) `void refreshDispatcherOwnedConversation(...)` роняло весь диспетчер unhandled rejection'ом, когда `thread/read` возвращал ошибку — теперь падение ловится на границе таймера и логируется; (2) refresh по notification'у для только что созданного треда всегда упирался в «not materialized yet», поэтому notification-путь обновляет только треды, у которых уже есть turns (turn, отправленный вебвью, обновляет безусловно — это и есть момент материализации).

### E4. Нарушение инварианта «один webview»: несколько вкладок/устройств — DONE

VS Code гарантирует один webview-инстанс; в бридже каждая вкладка — полноценный клиент. `mcp-request` (аппрувы) броадкастится всем SSE-клиентам (`extension-webview.ts:218-228`), а ответить может каждая вкладка: второй `respondToServerRequest` кидает «No pending app-server request» (`codex-app-server.ts:160`) → host-message-error 500 во второй вкладке. Плюс дрейф состояния между вкладками (ответы на host-запросы видит только запросившая вкладка). Нужно решение: либо single-active-client (остальные read-only/kick), либо дедупликация ответов на server requests.

Решение пользователя: один активный webview. Сделано: активной считается вкладка, последней открывшая event stream (`makeActive`); броадкасты уходят только ей, host-message от вытесненной вкладки получает 409, а сама вкладка — сообщение `dispatcher-webview-superseded` по своему стриму до того, как перестанет получать броадкасты. Шим (наш код, не экстеншн) перехватывает это сообщение, закрывает EventSource и показывает оверлей «Codex moved to another tab» с кнопкой перезагрузки — вместо тихо замёрзшего UI. Проверено живьём: двe curl-сессии SSE, первая получает `superseded` и 409 на host-message, вторая работает.

`handleMcpRequest` требует строковый `request.id` (`extension-webview.ts:595`), `handleMcpResponse` принимает string|number (`:667`). Числовой id запроса от экстеншна даст «Invalid mcp-request payload». Унифицировать.

### E8. Половина протокола «хост ↔ webview» выдумана нами и в вебвью не существует (найдено при изучении VS Code для E6) — DONE

Изучение бандлов под E6 вскрыло следующее. Клиентская координация (всё, что связано с IPC: following, thread-stream-state, queued-followups, archive/read-state, инвалидация кэша, IPC-**запросы** к другим клиентам) доступна вебвью **только** через объект `clientCoordination`, а он приезжает по отдельному RPC-каналу: вебвью постит хосту `{type:"vscode-capn-rpc-connect", sessionId}` и ждёт кадров `vscode-capn-rpc-message` (`webview/assets/app-initial-DoX22WEG.js`, класс транспорта + `await Pye.services`). Диспетчер этот канал не реализует (`grep -rn capn src/` — пусто), поэтому промис сервисов не резолвится никогда и все вызовы вида `Jp.clientCoordination?.…` — молчаливый no-op.

Симметрично, сообщения, которыми мы пытаемся заменить этот канал, вебвью не знает. По всему `webview/assets`: `ipc-broadcast` — 0 совпадений (то, что мы шлём в стрим на каждый IPC-броадкаст и в реплее), `thread-role-request`/`thread-role-response` — 0, `thread-stream-snapshot-request` — 0, `thread-follower-*-request`/`-response` — 0, `persisted-atom-reset` — 0. Входящие сообщения вебвью проверяет только на `typeof type === "string"` и молча игнорирует всё, чего нет в его `switch` — поэтому это не видно ни в логах, ни в ошибках.

Следствие: **режим follower'а на телефоне не работает вообще** — снапшоты тредов, которыми владеет окно VS Code, доезжают до диспетчера (`mirroredConversations`), но в UI не попадают; и вебвью не может ни объявить following, ни отправить follower-запрос владельцу. Работает ровно то, что диспетчер делает сам, минуя вебвью: он владеет тредами через свой app-server и отвечает окнам VS Code по IPC (проверено живьём в E3/E2).

Уточнение после E6 (адресные броадкасты): теперь окно VS Code шлёт снапшот только тем, кто объявил following, а объявить его за диспетчера некому — вебвью канала не имеет, а сам диспетчер объявляет following только на треды, состояние которых у него уже есть. Значит `mirroredConversations` пополняется исключительно через handover собственного owned-треда; тред, созданный в окне VS Code с нуля, диспетчер не увидит вообще. До E6 он получал такие снапшоты «за компанию» (броадкаст всем) — и всё равно не показывал их в UI по причине выше.

Выбран вариант (а) — реализовать канал по-настоящему, потому что изобретать в нём нечего: протокол внутри `vscode-capn-rpc-message` — это [Cap'n Web](https://www.npmjs.com/package/capnweb) в неизменном виде (в вебвью-бандле лежат её же токены `push`/`pull`/`pipeline`/`remap`/`export`/`promise` и `RpcTarget`, счётчики совпадают с npm-сборкой `capnweb@0.11.0` один в один), а обе половины интерфейса читаются из бандла целиком.

Сделано:

- `capnweb@0.11.0` — первая рантайм-зависимость проекта. Реализовывать чужой wire-протокол руками, когда библиотека опубликована, — это ровно тот случай, когда «своя реализация» хуже зависимости.
- `src/webview-rpc.ts`: транспорт поверх нашего же канала (`vscode-capn-rpc-connect` заводит сессию на вебвью, кадры `vscode-capn-rpc-message` ходят через тот же POST `/host-message` и SSE), очередь входящих кадров (капнвеб забирает их по одному — VS Code в своём транспорте `YP` буферизует так же), хостовый `clientCoordination` (12 методов класса `Yv` из `out/extension.js`: archive/unarchive, queued-followups, stream-state, following-changed/status-requested, read-state, invalidate-cache, `getIdeContext`, `findThreadOwner`, `requestThreadFollower`) и доставка входящих броадкастов в вебвьюшный сервис по таблице из `Yrt` с той же проверкой версии метода.
- Сессия живёт на вебвью, а не на процесс: реконнект вебвью открывает новую и старая закрывается, иначе один таб получал бы каждый броадкаст дважды.
- Удалён выдуманный протокол: `ipc-broadcast` в стрим и в реплее, `thread-role-request`/`-response`, `thread-stream-snapshot-request`, `thread-stream-resume-request`, мост follower-запросов сообщениями (`thread-follower-*-request`), `persisted-atom-reset`. Всё это в вебвью 26.803 отсутствует (0 совпадений по бандлам).
- Реплей `mirroredConversations` тоже удалён: IPC-состояние теперь приезжает по сессии, а reload вебвью пересоздаёт её и заново объявляет following — владелец отвечает свежим снапшотом.

Проверка: `tests/webview-rpc.test.ts` поднимает **настоящий** capnweb-клиент (`RpcSession` из npm-пакета) поверх реального SSE+POST канала нашего хоста, вызывает `clientCoordination.threadStreamFollowingChanged`/`requestThreadFollower` и проверяет, что они легли на IPC, а входящий броадкаст доехал до вебвьюшного сервиса; броадкаст с чужой версией метода отбрасывается. Фейкового транспорта в тесте нет — иначе он не доказывал бы совместимость с настоящей библиотекой.

По итогам ревью добавлено ещё две правки. Первая: `requestThreadFollower` несёт `timeoutMs` вызывающего, и он теперь доезжает до шины — расширение даёт `thread-follower-load-complete-history` пять минут (`Krt`), а наш мост резал любой запрос своим дефолтным таймаутом в 5 секунд. Вторая: RPC-сессия уходит вместе с «местом» активного вебвью — вытесненный таб отбивается на `/host-message`, так что его незакрытые вызовы ждали бы ответа, который уже некуда доставить.

Что осталось за рамками: остальные сервисы сессии (`openIn`, `fileAttachments`, `github`, `workspaceFiles`, `clipboard`, `appInfo`, …) хост не отдаёт. Раньше они молча висели вместе с нерезолвнутым `services`, теперь вызов такого сервиса даст ошибку в вебвью. Заглушки не ставим — это был бы деградированный режим; реализуем по мере того, как понадобится конкретная фича.

### E10. На `thread-owner-discovery` никто не отвечает — окно VS Code уводит тред у телефона — DONE

Найдено ревьюером по итогам E9. Помимо 13 follower-методов, расширение регистрирует на шине ещё один хендлер владельца — `thread-owner-discovery` (рядом с `wq` в `out/extension.js`: `canHandle = hostId === собственный && isOwner(conversationId)`, ответ — пустой объект; важен не он, а `handledByClientId` в конверте). Диспетчер отвечал на follower-методы, но не на discovery.

Последствие читается в `maybe_resume` вебвью: перед резюмом треда клиент спрашивает `findThreadOwner`, и **только** при непустом ответе становится follower'ом; при `null` он резюмит тред сам как владелец. То есть окно VS Code, открывшее тред, который прямо сейчас гоняет телефон, забирало rollout себе, а диспетчер по первому же чужому снапшоту отдавал владение — телефон терял живой стрим посреди турна. E9 починил только исходящее направление (наш вебвью спрашивает с правильной версией), входящее оставалось глухим.

Сделано: хендлер `thread-owner-discovery` с предикатом «наш `hostId` и тред всё ещё наш» — ровно как в расширении.

### E11. Ответ на `thread-follower-interrupt-turn` не соответствует v4 — DONE

Найдено ревьюером по итогам E9. Владелец в расширении отвечает `{interruptedTurnId: await interruptConversation(conversationId, mode, expectedTurnId), ok: true}`, а follower читает именно `interruptedTurnId`: в buffered-turn flow он сравнивает его со своим `turnId` и при несовпадении бросает «The buffered turn is …». Мы отвечали результатом `turn/interrupt` (или `{ok:true}`), то есть `interruptedTurnId === undefined` — сравнение не совпадало никогда. Заодно игнорировался `expectedTurnId`: follower просит остановить конкретный турн, а мы били по тому, что нашли в состоянии. До E9 этот путь вообще не доходил (v1 против v4 = version-mismatch), так что бамп версии его включил, а хендлер под него дотянут не был.

Сделано: `expectedTurnId` учитывается (несовпадение с текущим in-progress турном → `interruptedTurnId: null`, как в `Lze`), ответ несёт `interruptedTurnId`.

Осознанно не сделано: `mode` (`system`/`user-stop`/`descendant-cleanup`) диспетчер игнорирует — в расширении он управляет только зачисткой subagent-потомков (`interruptSubagentDescendants`), которой у нас нет вообще. Это отдельная фича, а не половина текущей правки.

### E12. Мерж `threadSettings` терял модель и effort, приехавшие внутри collaboration mode — DONE

Найдено ревьюером по итогам E9. Наш мерж брал `model`/`effort` только с верхнего уровня payload'а, а вебвью меняет модель **исключительно** через пикер режима: он шлёт `threadSettings: {collaborationMode: {...settings: {model, reasoning_effort}}}` и больше ничего. Эталон — `Cb` в вебвью: `model = t.model ?? t.collaborationMode?.settings.model ?? prev.model ?? latestModel`, аналогично effort (`bIe`), плюс резолв `permissions`/`sandboxPolicy` в `activePermissionProfile` (`vIe`), `cwd` и отметка `previousTurnModel` (`xIe`).

Следствия были двойные: (1) follower уже применил `Cb` у себя правильно, а наш снапшот перезаписывает его состояние целиком — выбранная модель откатывалась в UI; (2) следующий частичный апдейт пересобирал `settings.model` режима из протухшего `latestModel`, и `turn/start`, который берёт модель именно из режима, уезжал на старой модели. Дополнительно `permissions` оседали в `latestThreadSettings`, не превращаясь в `activePermissionProfile`, с которым стартует турн.

Сделано: `applyThreadSettingsUpdate` переписан построчно по `Cb` (`yIe`/`bIe`/`vIe`/`xIe` — отдельными функциями с теми же именами в комментариях). Прежний `updateCollaborationModeSettings` удалён: он был нашей приблизительной версией того же мержа и, в частности, затирал `reasoning_effort` режима в `null`, когда effort не менялся.

### E13. `load-complete-history` отвечал ревизией по треду, которым мы уже не владеем — DONE

Найдено ревьюером по итогам E9 (у него — minor). Владение может уехать прямо во время `await refreshDispatcherOwnedConversation`: приходит чужой снапшот, `releaseDispatcherOwnership` чистит все мапы, а продолжение хендлера заново заводило запись в `dispatcherOwnedRevisions` (её больше некому удалить) и отвечало follower'у ревизией по треду, которым мы уже не владеем — тот ждал бы её свои пять минут впустую. Настоящий владелец в такой ситуации бросает `no-client-found: thread stream owner became unavailable`.

Сделано: после refresh'а проверяем владение и бросаем ту же ошибку; `broadcastDispatcherOwnedSnapshot` не нумерует треды, которые нам уже не принадлежат.

### E14. Таймаут вызывающего не уезжал на шину — роутер резал всё на 10 секундах — DONE

Найдено ревьюером по итогам E10–E13, и это дыра в самой правке из E8: `timeoutMs` мы протащили только до локального таймера клиента, а в кадре запроса его не было. Между тем таймеров два: клиент ждёт `timeoutMs ?? 5s`, а **роутер** ставит свой поверх форварда — `setTimeout(…, request.timeoutMs ?? 10s)` (`Gye` в `out/extension.js`). Наш `sendRequest` собирал кадр без поля, а наш роутер и вовсе игнорировал присланное клиентом.

Следствия в обе стороны: наш вебвью-follower, запросивший у окна VS Code `thread-follower-load-complete-history` (5 минут по замыслу), получал `request-timeout` через 10 секунд; и симметрично — VS Code-follower нашего треда. Хуже того, follower трактует таймаут как «владелец пропал» (`markConversationNeedsResumeForUnavailableOwner`) и может забрать тред себе — тот же симптом, что в E10, только на длинных тредах.

Сделано: `timeoutMs` едет в кадре запроса, роутер использует `message.timeoutMs ?? 10s`. Тесты: кадр на проводе несёт дедлайн, и форвард отваливается по присланному дедлайну (60 мс вместо роутерных 10 с — проверено, что без правки тест падает).

### E15. Стоп, нажатый в момент завершения турна, бросал ошибку в UI follower'а — DONE

Найдено ревьюером по итогам E11 (у него — минорно). Наше состояние треда — throttled-копия, отстающая на 120 мс debounce плюс latency чтения, поэтому follower штатно просит остановить турн, который app-server уже завершил или сменил. App-server отвечает `ExpectedTurnMismatch` (называя реально идущий турн) или `no active turn to interrupt`. Эталон (`Lze` в вебвью) обе ошибки разбирает: при mismatch — повторяет interrupt по названному турну (если follower не просил конкретный другой), при «нет активного турна» — считает турн остановленным. Мы бросали как есть, а follower такие ошибки не глотает (его allow-list — только `no-client-found`/`timeout`/`request-version-mismatch`) и показывает в UI.

Сделано: `interruptDispatcherOwnedTurn` повторяет обе ветки `Lze`; парсеры сообщений (`mismatchedTurnId` — обе формы из `Fze`, `isNoActiveTurnError` — `Rze`) вынесены в `dispatcher-owner.ts` и покрыты тестами. Это не деградированный режим: это контракт `turn/interrupt`, у которого «турн только что кончился» — нормальный исход, а не отказ.

Поправка по итогам ревью: первая версия была мертворождённой. Наш клиент app-server заворачивал каждую ошибку в `` `${method}: ${message}` ``, а `Rze` в вебвью сравнивает строго — у расширения между app-server и парсером нет нашего слоя (`reject(new Error(e.error.message))`). Ветка «no active turn» не срабатывала никогда, и тесты этого не ловили, потому что кормили парсер голой строкой, которой в проде не бывает. Вместо матчинга по хвосту введён `AppServerError` с полем `reason`: сообщение по-прежнему с префиксом (он нужен в логах), а слова app-server'а доступны отдельно и не требуют разбора собственного форматирования.

### E16. Наш префикс метода уезжал наружу — вебвью и follower не узнавали слова app-server'а — DONE

Найдено ревьюером по итогам E15: правка E15 закрыла только один путь из трёх. VS Code пересылает ошибку app-server **как есть**: в `mcp-response` летит сырой объект (`message:{id, result: e.result, error: e.error}`), а на IPC-границу уходит голое `error.message`. Мы же на обеих границах отдавали своё `${method}: ${message}`.

Что из-за этого ломалось:

- **Основной путь владельца.** `Lze` (стоп с обработкой гонки) исполняется в самом вебвью, который мы хостим, и ходит в app-server через `mcp-request`. Его `Rze` сравнивает строго — с префиксом не совпадало никогда, то есть стоп, нажатый в момент завершения турна, показывал ошибку в UI телефона. Тот же catch ломал строго матчащуюся ветку `no active turn to steer`.
- **IPC-путь.** `thread-follower-steer-turn` пробрасывал `AppServerError` на шину, follower получал `turn/steer: no active turn to steer` и вместо штатного превращения стира в обычное сообщение показывал ошибку.

Сделано: `AppServerError` несёт ещё и `payload` — сырой JSON-RPC error app-server'а, который мост отдаёт вебвью без изменений; на IPC-границе ответ владельца отдаёт `reason`. Префикс остаётся там, где он и был полезен, — в `message` для логов и `host-message-error`.

Хвост, найденный тем же ревью: эндпоинт `vscode://codex/ipc-request` (и вся проводка `handleIpcRequest`/`handleExtensionIpcRequest`) — наша выдумка того же класса, что удалённое в E8: литерала `ipc-request` нет ни в `out/extension.js`, ни в `webview/assets` 26.803, вебвью ходит на шину только через capnweb-сессию. Удалён вместе с тестом на него, а не завёрнут «для симметрии».

### E17. Диспетчер и расширение сидели на разных шинах — follower-режима не существовало вообще — DONE

Найдено при попытке пройти ручной сценарий: `/debug` показывал `bridge.ipc.status: connected`, `peers: []`, и так было бы у любого пользователя. Диспетчер знал ровно один путь до шины — legacy `$TMPDIR/codex-ipc/ipc-<uid>.sock`; расширение 26.803 резолвит эндпоинт в другом порядке (`getOrStartRouterEndpoint` в `out/extension.js`):

1. `gT()` = `${CODEX_HOME ?? ~/.codex}/ipc/ipc.sock` — если туда получается подключиться, это и есть шина;
2. иначе `Lye()` = `$TMPDIR/codex-ipc/ipc-<uid>.sock` — но только если сокет наш по uid и живой (совместимость с уже запущенным старым клиентом);
3. иначе — снести протухший `gT()` и поднять роутер там.

Win32 — именованный пайп `\\.\pipe\codex-ipc`, без вариантов.

На живой машине `~/.codex/ipc/ipc.sock` уже поднят окном VS Code, поэтому оба окна сидели там, а диспетчер — один на своём сокете. Оба «подключены», оба здоровы, и ни один пункт follower-режима (E8–E16) физически не мог отработать: ни discovery, ни снапшоты, ни стоп с чужой стороны.

Сделано: `codexIpcEndpoint()` / `legacyCodexIpcSocketPath()` / `IpcRouterManager.resolveEndpoint()` повторяют этот порядок; директория `ipc` создаётся с правами 0700 и проверяется на владельца (как `gT()`). Эндпоинт резолвится в `start()` и виден в снапшоте, чтобы `/debug` отвечал на вопрос «на какой шине мы вообще сидим».

Проверки владения скопированы вместе с порядком — они часть того же решения, а не украшение (найдено ревьюером, все три сверены с бандлом):

- `$ye`: legacy-сокет принимается, только если он наш **и** его директория наша и закрыта для group/other (`mode & 0o22`). `/tmp/codex-ipc` с правами 0777 расширение отвергнет и уйдёт на primary — дисптечер, который его примет, снова окажется на другой шине.
- `Bye`: после `listen` сокет проверяется на владельца и получает 0600; иначе сервер закрывается. Umask — не то место, где решаются права на шину.
- `Fye`: сносим протухший сокет, только если он наш; чужой файл на этом пути — не наш мусор.

Проверка: пять тестов в `tests/codex-ipc.test.ts` — три на порядок резолва (пустой `CODEX_HOME` → хостим primary; кто-то уже на primary → подключаемся туда и видим друг друга в `peers`; primary мёртв, legacy живой → уходим на legacy и primary не создаём) плюс отказ от legacy в открытой всем директории и права 0600 на поднятом сокете.

### E18. Хост ходил в backend-api анонимно — вебвью не доходил до первого экрана — DONE

Найдено сразу после E17, при первой же попытке открыть вебвью в браузере: приложение висело на сплэше с логотипом. ### E20. Прокси бэкенда сдавался на первом обрыве сети и не умел отменять запросы — DONE

Ревью E18 сверило нашу копию `cP.fetch` с бандлом построчно и нашло то, что при чтении своего же кода не видно: у нас есть ретраи по статусу, но нет ретраев по **броску**. В бандле `catch` внутри попытки делает `backoffDelay(c)` и повторяет ровно как на 5xx, и только исчерпав бюджет отдаёт `status: 432`. У нас исключение из `fetch` улетало во внешний catch и приходило в вебвью как `error 501` без единой повторной попытки: моргнувшая сеть, которую расширение молча переживает, у нас становилась ошибкой в UI.

Заодно приведено к оригиналу всё остальное из `cP.fetch`:

- **`cancel-fetch`.** Раньше игнорировался (`default: return []`). Вебвью при отмене реджектит свой промис сам, так что зависания не было, но наш запрос продолжал идти и тратить rate limit аккаунта на ответ, которого никто не ждёт. Теперь на каждый внешний fetch заводится `AbortController` в реестре по `requestId`, `cancel-fetch` его дёргает, отменённый обмен отвечает `status: 499, error: "Request cancelled"` — как `cP.cancel`.
- **Не-2xx.** Отдаём `responseType: "error"` со `statusText`, как расширение, вместо прежнего `success` с телом (см. отменённый абзац в E18).
- **Тело 2xx.** `JSON.stringify(await response.json())` для `application/json` без `x-codex-binary-response` — кривой JSON теперь честно падает в ретрай и 432, а не доезжает до вебвью сырым текстом.
- **`x-codex-base64`** удаляется безусловно, а не только в ветке с телом: на GET он утекал бы на сервер.
- **`User-Agent`.** Расширение шлёт `initializeResult.userAgent ?? "codex_vscode"` (`setUserAgent` из ответа app-server) — мы не слали ничего, и бэкенд видел дефолтный UA Bun'а. Проверено на живом app-server: `initialize` возвращает `userAgent: "codex_mobile_dispatcher/0.145.0 (Mac OS 14.6.1; arm64) ..."`, собранный из нашего же `clientInfo`.

Осознанное отличие (единственное): у расширения таймаута на запрос нет вообще, у нас общий на весь обмен — 25s на все попытки сразу. Причина не в аккуратности, а в транспорте: relay сдаётся на 30s, и ответ, приехавший позже, до вебвью уже не доедет. Дедлайн терминальный: сработал — ретраев больше нет.

Проверка: тесты на ретрай броска (`fetch` кидает на первой попытке, вторая проходит) с проверкой `User-Agent` из initialize, на отмену (499 приходит раньше, чем ответил бы origin), и переписанный тест не-2xx.

Ревью коммита нашло четыре остаточных расхождения с `cP.fetch` (закрыты в E26), ни одно не блокирует, но все того же рода, что закрывал E20: (1) `vscode://codex`-ветка обрабатывается **до** создания `AbortController`, поэтому `cancel-fetch` на неё — no-op, тогда как бандл регистрирует контроллер до ветвления и прокидывает `signal` в `handleVSCodeRequest`; (2) в ветке ретрая по статусу дедлайн не проверяется перед сном, так что обмен может пережить заявленные 25s примерно на 2.4s; (3) внешний catch отдаёт `501` там, где расширение отдаёт `433`; (4) до `initialize` расширение не шлёт заголовок `User-Agent` вовсе, а мы шлём фолбэк. Плюс не закреплено тестами: исчерпание бюджета (4 попытки → 432 с сообщением последней ошибки), сам дедлайн, ретрай на кривом JSON и то, что `x-codex-base64` не утекает на GET.

Открытый хвост: `fetch-stream` (`cP.stream`) — закрыт в E27; `get-settings` — всё ещё открыт.

### E21. Follower падает на нашем снапшоте: мы шлём форму app-server, а вебвью ждёт свой стор — DONE

Найдено при прогоне `docs/manual-verification-follower.md` (Check 0). Хендшейк проходит целиком: VS Code пишет `thread_stream_role_changed ... role=follower`, наш `/debug` показывает `followers: [...]`, `hostErrors` пуст. И сразу после этого вебвью VS Code падает в `LocalConversationPage`: `TypeError: Cannot read properties of undefined (reading 'input')`, при попытке продолжить — `Failed to resume chat / Cannot read properties of undefined (reading 'settings')`. В браузере это не видно никогда: там наш вебвью сам owner и наш снапшот не потребляет.

Причина установлена по бандлу, гадать не пришлось. Owner отдаёт в `conversationState` **дословно свой стор**:

```js
sendConversationSnapshot(e,t,n){if(this.getStreamRole(e)?.role!==`owner`)return!1;let r=this.params.threadStore.getConversation(e);return r?(this.params.ipcBridge.threadStreamStateChanged?.({conversationId:e,hostId:this.params.hostId,targetClientIds:t,change:{type:`snapshot`,revision:n,conversationState:r}})...
```

Follower его принимает через `zPe` → `BPe` → `LPe`: нормализуются только даты (`createdAt/updatedAt/recencyAt`, `turnStartedAtMs`, `firstTurnWorkItemStartedAtMs`, `finalAssistantStartedAtMs`), `title`, `turnHistory.history.entitiesByKey`, и добавляются дефолты `hostId`/`turnsPagination`/`workspaceKind`. Всё остальное кладётся в стор как есть. То есть контракт снапшота — это внутренний объект `Conversation` вебвью, а не тред app-server.

Мы же (`conversationFromThread` в `src/server.ts`) разворачиваем в снапшот сырой ответ `thread/read`. Турн app-server — это `{id, items, itemsView, status, error, startedAt, completedAt, durationMs}` (проверено на живом `codex app-server`), а вебвью читает у турна `params.input`, `turnId`, `turnStartedAtMs`, `durationMs`, `finalAssistantStartedAtMs`, `commandExecutionStartedAtMsById`; отсюда и `undefined.input`.

Конструктор разговора — `VIe`, полный список полей: `id, sessionId, forkedFromId, hostId, turns, requests, createdAt, updatedAt, recencyAt, title, source, threadSource, historyMode, parentThreadId, mode, threadStartKind, modelProvider, latestModel, latestReasoningEffort, previousTurnModel, latestCollaborationMode, hasUnreadTurn, threadRuntimeStatus, rolloutPath, gitInfo, resumeState, latestTokenUsageInfo, workspaceKind, workspaceBrowserRoot, projectlessOutputDirectory, cwd` (+ `turnsPagination`, `turnHistory` при канонической истории).

Маппер турнов app-server → стор в бандле уже есть готовый, это `jy` (обёртки `ePe`/`Ay`/`$Ne`), ~25 строк: `params.input` берётся из `itemsPaginationByTurnId[id].oldestUserInput` либо из первого `userMessage.content`, `turnStartedAtMs = startedAt*1000`, `finalAssistantStartedAtMs = completedAt*1000`, `permissionParamsSource: "inferred"`, items прогоняются через `nPe`/`rPe` (только `imageGeneration` и `collabAgentToolCall` меняются).

Побочно подтвердилось главное про архитектуру: **в расширении хост — тупая труба**. В `out/extension.js` нет ни стора разговоров, ни `getStreamRole`, ни `thread-role-for-host`. Вся раздача ролей и обслуживание follower-запросов — `wq({hostId, ipcClient, viewService})`: `canHandle` каждого `thread-follower-*` = «вебвью говорит, что он owner» (`viewService.getThreadRole`), сам хендлер = `Zrt` → `viewService.requestThreadFollower`, а все broadcast'ы просто пересылаются в вебвью (`Yrt`). `thread-owner-discovery` устроен так же и возвращает пустой `{}` — важен только `handledByClientId`. Наш диспетчер вместо этого держит этот мозг у себя (`dispatcher-owner.ts` + `dispatcherOwnedConversations` в `server.ts`), и расхождение формы — прямое следствие.

Два выхода, оба реальные:

- **A. Стать трубой, как расширение.** Наш хост уже держит обратный стаб вебвью (`getRemoteMain().services.clientCoordination` в `src/webview-rpc.ts`), а на нём у вебвью есть ровно нужные `getThreadRole` и `requestThreadFollower` — то есть плюс два метода и перепроводка, минус ~300 строк owner-логики. Цена не в коде: owner существует только пока подключён вебвью. Телефон закрыли — тред не наш, хотя турн у нас в app-server всё ещё идёт, и VS Code, открыв его, отрезюмит тот же rollout на своём app-server. Это ровно то, ради чего диспетчер и писался, так что A ломает продукт, а не архитектуру.

Объём — маппинг + тесты, ревизии, `latest*` и `requests` у нас уже свои.

Выбор — B: диспетчер обязан владеть тредом без подключённого вебвью, а цена B ограничена одним маппером.

Сделано по варианту B. `buildOwnerConversationState` — построчный порт `VIe` (включая `Ob`: секунды на проводе, миллисекунды в сторе), турны — порт `jy` с `permissionParamsSource: "inferred"`, `Jr`/`jr` (профиль разрешений против sandbox-политики) и `rPe` для `collabAgentToolCall`. Два места портировать не стали, оба названы в коде: `Eae` (аттачменты вытаскиваются обратно из текста сообщения — у нас на dispatcher-owned турне не будет чипсов над сообщением, сам текст с блоком упоминаний виден) и `jg` для `imageGeneration` (переписывает путь в webview-URI **своего** вебвью, в чужом он всё равно бессмыслен).

Проверка на живой границе: изолированный `CODEX_HOME`, диспетчер держит шину, второй диспетчер на той же шине открывает наш тред и становится follower'ом — то есть снапшот потребляет настоящий бандл расширения. `/debug` owner'а показывает follower'а, `hostErrors` пуст с обеих сторон, снятый с шины снапшот (probe, объявивший `thread-stream-following-changed`) — ровно `VIe`: 31 поле, `createdAt/updatedAt/recencyAt` в миллисекундах, `resumeState: resumed`. Падения `undefined.input` больше нет ни на одной стороне. Чего эта проверка ещё не показала — отрисованный турн: `turns` в снапшоте пуст всегда, и это отдельный баг, см. E23.

Ревью порта нашло два расхождения, оба исправлены и закрыты тестами: (1) `latestCollaborationMode` мы отдавали `null`, а в бандле это поле не бывает null — оба вызова `VIe` передают `{mode:"default",settings:{model:"",reasoning_effort:null,developer_instructions:null}}`, и читается оно без guard'ов (`e.latestCollaborationMode.settings.model`), то есть это был тот же краш, что и E21, одним полем в сторону; (2) title мы брали из `thread.title`, которого у треда app-server нет вовсе — оба call-site'а `VIe` берут его из `Fb(thread.name)`, так что у follower'а тред был безымянным. Живьём после правки: в снапшоте `title: "Say ok again"` и дефолтный mode, турн из follower'а доезжает до app-server'а owner'а и обе стороны показывают ответ.

Открытый хвост разведки: живой снапшот от настоящего owner'а снять не удалось — VS Code не успевает поднять вебвью (`Webview did not finish starting` → «Codex could not start»), потому что машина под load average ~134 от постороннего ffmpeg. Это внешнее, к мосту отношения не имеет, и на форму ответа не влияет: контракт вычитан из продюсера и консьюмера напрямую. Проверять маппинг всё равно придётся на живом follower'е.

Вторая находка, отдельная от E21 — см. E22 ниже; разбираться с ней решено первой, потому что без живой шины проверять follower нечем.

### E22. Шина умирала молча: мы сносили чужой живой сокет и уходили не попрощавшись — DONE

Симптом, из-за которого встала проверка follower'а: `/debug` показывает `peers: []` и `status: connected` одновременно, `thread-owner-discovery` отвечает `no-client-found`, broadcast от пробника не долетает ни в одно окно VS Code — при том что оба окна живы и ничего не логируют. Лечилось только перезагрузкой окна.

Механика восстановлена по бандлу и подтверждена живьём. У расширения два свойства, которые вместе делают любую потерю сокета необратимой:

- `getOrStartRouterEndpoint` **удаляет** то, что лежит на эндпоинте, как только его проба туда не достучалась (`Fye(e)`), и сразу биндит своё;
- `routerStarted` — защёлка на всю жизнь процесса: она выставляется в колбэке `listen` и не сбрасывается никогда. Роутер, у которого из-под ног убрали файл сокета, продолжает слушать недостижимый inode, его собственный клиент к нему подключён и не рвётся — и второй раз поднять роутер он уже не может.

Отсюда две наши ошибки, обе исправлены:

- **Мы сносили живой сокет.** `startRouter` шёл `проба → unlink → listen`, и между пробой и unlink кто угодно успевал забиндиться. Теперь порядок обратный: `listen` первым, и только на `EADDRINUSE` мы пробуем подключиться; удаляем файл, лишь если на нём никто не отвечает. Заодно `stop()` больше не удаляет файл, который уже не наш — раньше выход диспетчера мог унести с собой сокет чужого роутера.
- **Мы уходили не попрощавшись.** `IpcRouter.stop()` закрывал сервер, оставляя принятые соединения открытыми. Расширение переподключается **только** по `close` — то есть брошенный нами роутер забирал с собой всех, кто на нём висел. Теперь при остановке роутера соединения рвутся явно, после того как по ним отправлены ответы `server-closed`.

И третье, уже про нашу собственную слепоту: потерю эндпоинта не слышит ни сервер, ни клиент, поэтому её приходится **смотреть**. Раз в секунду сверяем inode сокета, на котором стоит шина, с тем, к которому мы подключились; расхождение — это чужая шина на нашем пути, мы бросаем осиротевшее соединение, и дальше отрабатывает обычный реконнект с новыми выборами.

Проверка: тест на подмену сокета под работающим роутером — и хозяин, и его клиент оказываются на новой шине, а raw-клиент (тот, что переподключается только по `close`, как расширение) получает разрыв. Живьём: диспетчер держит роутер, два окна VS Code на нём; сторонний процесс удаляет сокет и биндит свой — через 2 секунды на новой шине оказываются все трое. До фикса тот же прогон оставлял `peers: []` на всё время наблюдения, а окна VS Code — мёртвыми до перезагрузки.

Чего мы починить не можем: защёлка `routerStarted` живёт в расширении. Если окно VS Code успело побыть роутером и его сокет подменили не мы, это окно останется вне шины до перезагрузки окна — наша сторона на это влиять не может.

### E23. Тред, который ведём мы сами, доезжал до follower'а пустым — DONE

Найдено сразу после E21, на первой же живой проверке: снапшот правильной формы, follower его принимает, `hostErrors` пуст — и `turns: []` всегда, сколько бы турнов в треде ни прошло. Ревизия у owner'а стояла на 2 и не двигалась.

Причина — взаимная блокировка в условии обновления. Refresh по нотификациям был закрыт вопросом «а есть ли уже турны в **нашей** копии разговора» (`dispatcherOwnedThreadHasTurns`), а турны в нашу копию попадают только из того самого `thread/read`, который это условие и охраняет. Ворота, которые открываются ключом, лежащим за воротами. Работало это лишь случайно: единственный безусловный refresh идёт по `turn/start` от вебвью с задержкой 0, и если `thread/read` успевал прочитать тред раньше, чем app-server записывал турн, — тред оставался пустым навсегда.

Гейт нужен, но спрашивать надо не себя, а app-server: `thread/read` действительно отказывается читать турны до первого пользовательского сообщения. Поэтому теперь ждём нотификацию `turn/started` (проверено на живом app-server: `turn/started :: threadId,turn`, все `item/*` тоже несут `threadId`) и с этого момента обновляемся по каждой нотификации треда.

Проверка на живой границе (изолированный `CODEX_HOME`, owner-диспетчер + follower-диспетчер на одной шине, вебвью — настоящий бандл расширения): снапшот несёт турн (`turnId`, `params.input`, `items: [userMessage, agentMessage]`, `turnStartedAtMs` в миллисекундах), ревизия растёт 2 → 9, follower открывает тред и показывает историю. Новый турн у owner'а follower видит живьём: «1 chat in progress» → «Thinking» → стрим ответа, `hostErrors` пуст с обеих сторон. Это и есть Проверка 0 из `docs/manual-verification-follower.md`.

### E24. Настройки треда жили только у нас в памяти — две стороны моста показывали разные модели — DONE

Найдено на Проверке 3 из `docs/manual-verification-follower.md`. Follower переключает reasoning effort на High, чип у follower'а становится High, наше состояние owner'а тоже (`latestReasoningEffort: high` в снапшоте на проводе) — а вебвью самого диспетчера продолжает показывать Medium. Обратное направление ломалось так же: смена effort в вебвью диспетчера не доезжала до follower'а вообще (два снапшота на шине после клика, оба со старым `effort`).

Причина одна на оба направления: настройки треда мы держали **только** в своей копии разговора. `thread-follower-update-thread-settings` правил её и рассылал снапшот — и всё; ни app-server, ни вебвью, подключённое к нам, об этом не узнавали. Смена в вебвью, наоборот, уходила в app-server (`thread/settings/update`) мимо нас: `thread/read` настройки не отдаёт (в треде их просто нет — `id, sessionId, preview, status, path, cwd, name, turns, …`), а `buildOwnerConversationState` берёт `latestModel`/`latestReasoningEffort` только из предыдущей копии. Собственный broadcast вебвью до follower'а не доходит: в его сторе нет наших follower'ов, и `targetClientIds: []` гасит рассылку на нашей же границе.

Так расширение и не делает. `updateThreadSettingsForNextTurn` в вебвью — одна функция на оба случая: follower уходит запросом к owner'у, а owner **всегда** зовёт `thread/settings/update` у app-server'а и только потом кладёт настройки в свой стор. Запрос follower'а owner обрабатывает той же функцией (`thread-follower-update-thread-settings-for-host` → `updateThreadSettingsForNextTurn`). То есть источник истины — app-server.

Сделали так же: запрос follower'а уходит в `thread/settings/update`, а наша копия разговора обновляется из нотификации `thread/settings/updated` (проверено на живом app-server: `{threadId, threadSettings: {cwd, approvalPolicy, sandboxPolicy, activePermissionProfile, model, effort, collaborationMode, …}}` — полный объект настроек). Эта же нотификация уезжает в подключённое к нам вебвью, которое её и так умеет обрабатывать. Одна точка истины, оба направления бесплатно.

Проверка на живой границе (owner-диспетчер 8792 + follower-диспетчер 8793, оба вебвью — настоящий бандл): High из follower'а — чип у owner'а High; Medium из owner'а — чип у follower'а Medium; следующий турн, отправленный из follower'а, идёт с выбранным effort (`reasoning_effort: "high"` в `turn_context` роллаута против `low` у предыдущего турна). Это Проверка 3.

### E25. Вебвью не поднимается по тому самому адресу, который диспетчер печатает как «Open from phone» — DONE

Найдено при попытке развести вкладки по разным хостам. Страница по `http://192.168.31.240:8794/` (и по `http://10.8.1.1:8795/`) остаётся пустой: 33 узла DOM, `TypeError: crypto.randomUUID is not a function` в `webview/assets/app-initial-*.js` на этапе инициализации модуля. То же самое приложение по `http://127.0.0.1:8792/`, `http://localhost:8793/` и `http://c.localhost:8794/` работает.

Причина не в нашем коде: браузер считает secure context только `localhost`, `127.0.0.0/8`, `*.localhost` и HTTPS. По LAN-адресу `window.isSecureContext === false`, а значит нет ни `crypto.randomUUID`, ни `crypto.subtle` — и бандл расширения падает на первом же обращении к ним. В VS Code вебвью всегда живёт в secure context (`vscode-webview://`), поэтому расширение и не защищается от этого.

То есть основной сценарий диспетчера — открыть его с телефона по адресу, который он сам печатает при старте, — сейчас не работает ни в одном современном браузере. Проверки follower'а мы прогоняли с двух loopback-хостов, и это скрывало проблему.

Варианты (нужно решение):

1. **HTTPS у диспетчера** (self-signed или mkcert): единственный вариант, который делает контекст по-настоящему secure и чинит заодно `crypto.subtle`. Цена — сертификат надо принять на телефоне (или доверить локальный CA).
2. **Тоннель с валидным сертификатом** (Tailscale Serve, ngrok): не трогаем код, но появляется внешняя зависимость и чужой TLS-терминатор в пути.
3. **Полифилл `crypto.randomUUID` перед бандлом**: снимает симптом на LAN-адресе, но `crypto.subtle` полифиллом не заменить — это была бы ровно та деградированная ветка, которую мы себе запретили, да ещё и с криптографией внутри.

Выбран вариант 1. Диспетчер слушает TLS с самоподписанным сертификатом, который сам же и выпускает (openssl, 825 дней — предел доверия у Apple) в `~/.codex-dispatcher/tls` при первом старте. В SAN попадают `localhost`, петля и все текущие LAN-адреса; если машина отвечает по адресу, которого в сертификате нет, он перевыпускается — иначе телефон упрётся в предупреждение, которое нельзя пролистать. При старте печатается путь и SHA-256 отпечаток: это единственное, с чем телефон может сверить то, что ему предлагают принять.

Выключается ровно там, где TLS терминирует кто-то перед нами: CLI поднимает диспетчер с `DISPATCHER_TLS=off` для relay и для cloudflare-тоннеля, оба ходят к нему по петле.

Проверка на живой границе: `https://192.168.31.240:8792/` — `isSecureContext: true`, `crypto.randomUUID` на месте, список тредов рисуется, тред открывается, `hostErrors` пуст. По `http://` тот же адрес давал 33 узла DOM и падение бандла. Известное ограничение самоподписанного сертификата: service worker не регистрируется (`Failed to register a ServiceWorker … SSL certificate error`), то есть установка PWA и офлайн-режим требуют сертификата, которому устройство доверяет по-настоящему.

Правки после ревью первой версии фикса. Первая версия читала SAN через `openssl x509 -ext subjectAltName`, а на стоковой macOS `openssl` — это LibreSSL, где такой опции нет: сертификат выпускался и тут же признавался негодным, то есть со второго старта диспетчер падал бы в цикл перевыпуска ровно на той машине, для которой всё это писалось. Теперь читается `-text`, который понимают обе реализации. Заодно: срок жизни проверяется (`-checkend 0`), нечитаемый или обрезанный `cert.pem` больше не блокирует старт навсегда — он просто повод выпустить новый, а ключ после генерации получает `0600` (OpenSSL ставит его сам, LibreSSL — по umask). `doctor` теперь проверяет наличие `openssl` в тех режимах, где TLS терминируем мы сами. Ревью самого фикса добавило ещё две: `chmod 0600` стоял внутри генерации, то есть до уже лежащего на диске ключа, выписанного LibreSSL, не доезжал — теперь он безусловный; и битый `key.pem` при валидном `cert.pem` был той же стеной, что и битый `cert.pem` (падение внутри `Bun.serve` на каждом старте, без перевыпуска) — теперь ключ проверяется через `openssl pkey -noout`, а не одним фактом существования файла. Проверено вживую на LibreSSL 3.3.6: старый 0644-ключ поджимается до 0600 без перевыпуска, обрезанный ключ приводит к выпуску новой пары.

### E26. Остаточные расхождения с `cP.fetch`: отмена не доходила до follower-веток, дедлайн не был терминальным — DONE

Хвост E20, найденный ревью того коммита. Три вещи из четырёх оказались настоящими, четвёртая при проверке — нет.

**Отмена не доходила до `vscode://codex`.** `AbortController` заводился уже после ветвления, так что `cancel-fetch` по follower-вызову был no-op. А это ровно та ветка, где ждать дольше всего: follower-запрос уходит по шине другому клиенту, и после E14 этот запрос ждёт столько, сколько попросил вызывающий, — минуты на `load-complete-history` большого треда. Теперь контроллер регистрируется до ветвления (как в бандле), сигнал прокидывается в follower-путь и дальше в `ipcBridge.request`, а `sendRequest` по аборту снимает pending-запись и реджектит `cancelled`. Слушатель снимается при любом исходе, так что подписки на сигнал не копятся.

**Дедлайн не был терминальным, хотя объявлен таким.** 5xx, приехавший на 24.9 секунде, отправлял нас спать полный backoff и только потом упираться в просроченный дедлайн: обмен переживал заявленные 25 секунд примерно на 2.4. Теперь ожидание между попытками обрывается вместе с дедлайном, и просроченный обмен отвечает тем статусом, который держит в руках, вместо заведомо мёртвой попытки.

**Внешний catch отдавал 501 там, где расширение отдаёт 433.** Наш собственный отказ (не отказ бэкенда) вебвью читает по коду; 501 — чужое слово.

**А вот `User-Agent` до `initialize` трогать не стали.** Расширение действительно не шлёт заголовок, пока app-server не назвал клиента, и первым порывом было повторить это. Проверка показала обратное: `fetch` в Bun при отсутствии заголовка сам подставляет `Bun/1.3.3`, то есть «не слать» у нас означает «слать имя рантайма» — в бэкенд OpenAI. Расширение в этой же ситуации падает на `Pf` (`codex_vscode`), так что наш прежний фолбэк ближе к оригиналу, чем формальное совпадение с ним. Оставлено как есть, зафиксировано тестом.

Тестами закреплено то, что E20 оставил незакрытым: исчерпание бюджета (4 попытки → 432 с сообщением последней ошибки), ретрай на кривом JSON в 2xx, отсутствие `x-codex-base64`/`x-codex-binary-response` в GET-запросе к origin, и отмена follower-вызова. Сам дедлайн тестом не закреплён сознательно: честная проверка стоит 25 секунд стены в юнит-сьюте, а поведение после его срабатывания — общий код с отменой.

### E27. `fetch-stream` хост не реализовывал — стриминговый вызов молча висел вечно — DONE

Вебвью зовёт `Fd.stream()` для `POST /codex/responses` (генерация через бэкенд: заголовки тредов и прочие короткие ответы). У стрима, в отличие от `fetch`, нет ответа на запрос: всё, включая сам факт «ответа не будет», — это отдельные сообщения хоста (`fetch-stream-response` / `-event` / `-complete` / `-error`). Мы не отвечали ничем, вебвью держал handler и ждал вечно. Молчаливое зависание хуже видимой ошибки — оно не оставляет даже следа в `hostErrors`.

Порт `cP.stream` целиком: тот же сбор заголовков, что у `cP.fetch`, ретраи (401 с рефрешем токена, ретраибельные статусы, брошенное исключение) с тем же бюджетом и backoff, `cancel-fetch-stream` через `AbortController`. Разбор тела — оба формата бандла: `ndjson` (`B5`) и SSE (`mve` + `_N`), включая обе версии пустой строки между событиями (`\n\n` и `\r\n\r\n`) и отбрасывание `heartbeat`. Обратно уезжают только те пять тайминговых заголовков, которые перечисляет `F5`, — остальные заголовки ответа вебвью не показываются вообще.

Осознанное отличие от `cP.fetch`: **дедлайна нет**. У унарного прокси он есть потому, что relay сдаётся на 30 секундах и ответ, приехавший позже, до вебвью не доедет; события же стрима едут по собственному SSE-каналу вебвью, а длинный ответ — ровно то, ради чего стрим и нужен. Отмена — единственный способ его прервать, как в расширении.

Отменённый стрим завершается `-complete`, а не `-error`: вебвью сам его отменил и уже выбросил накопленное — ошибка тут была бы новостью о том, что он и так знает. Это поведение бандла (`n.signal.aborted||fve(f)`).

Проверка: тесты на SSE-поток целиком (пропуск heartbeat, событие без имени, только тайминговые заголовки, `-complete` в конце), на отказ бэкенда (`403 Forbidden` → `-error`, а не тишина) и на отмену (origin видит закрытие соединения, вебвью получает `-complete`).
